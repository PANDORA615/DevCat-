# DevCat — полное техническое задание на образовательную платформу и IDE

> Версия ТЗ: 1.0 · 27 октября 2026 · Статус: спецификация для поэтапной реализации в Codex.
>
> **Название продукта: DevCat.** Целевые платформы: Android, Windows, macOS, Linux. Язык интерфейса на старте — русский; архитектура локализации для других языков.

## 0. Главный принцип реализации

Создать **реально работающий продукт**, а не набор экранов-заглушек: полноценное обучение, практические задания, локальная или изолированная удалённая среда исполнения, файловые проекты, Git и IDE. Девять направлений: **C, C++, C#, Python, Java, JavaScript, Go, SQL, Git/GitHub**. Git/GitHub — самостоятельная вкладка и курс, а не язык программирования.

**Требование «абсолютно все знания» интерпретировать как долгосрочную цель максимально полного, непрерывно актуализируемого и проверяемого покрытия.** Невозможно гарантировать знание всех существующих библиотек, нестабильных расширений, версий, багов и частных случаев. Поэтому внедрить версионированный каталог языков, стандартов, библиотек, справочников, диагностик, источников, тестов покрытия и редакционный процесс обновлений. Никаких заявлений «100% всех знаний» без формальных метрик.

**«Собственный компилятор» означает собственный встроенный сервис компиляции DevCat с управлением toolchain и единым интерфейсом**, а не написание с нуля компилятора C/C++/C#/Java/Go. Использовать проверенные компиляторы и рантаймы с соблюдением лицензий: Clang/GCC, .NET SDK/Roslyn, OpenJDK, Go, CPython, Node.js. Для SQL — локальный SQLite и изолированные серверные экземпляры PostgreSQL; для JS и Python — интерпретаторы/рантаймы. Не выдавать обёртку над сторонними toolchain за собственную реализацию компилятора.

## 1. Видение и пользовательские сценарии

DevCat совмещает (1) интерактивные курсы с теорией, задачами, тестами и объяснениями ошибок; (2) самостоятельную IDE с проектами, редактором, терминалом, отладкой и Git; (3) персонального пиксельного кота-наставника; (4) справочник по языкам, инструментам и библиотекам.

Основные сценарии: новичок выбирает Python и проходит первый урок; опытный разработчик изучает Go; студент сравнивает C и C++; пользователь пишет многофайловое C#-приложение, подключает NuGet и запускает тесты; изучающий SQL выполняет запросы в учебной базе; пользователь проходит практику `git clone`, `branch`, `commit`, `push`, PR и SSH; на Android пишет код и запускает его в безопасном облачном runner; на ПК работает с локальными компиляторами без интернета.

Принципы: offline-first для чтения скачанных курсов и локальных проектов; честные статусы недоступных онлайн-функций; доступность; безопасность выполнения кода; пользователь контролирует данные и тему; никакого принудительного фиолетового оформления.

## 2. Платформы и технологии

**Клиент:** Flutter + Dart для Android и Windows/macOS/Linux, Material 3, адаптивная навигация. Для IDE интегрировать зрелый редактор через нативный компонент или WebView с Monaco/CodeMirror 6 (выбор после технического прототипа); проверить IME, accessibility, клавиатуру, выделение, большие файлы, производительность на Android. Flutter-приложение должно быть работоспособно без backend для офлайн-уроков и просмотра файлов.

**Сервер:** API (например, Go или Kotlin), PostgreSQL, Redis для очередей/кэша, объектное хранилище S3-совместимого типа, сервис аутентификации, отдельные изолированные execution workers, сервис синхронизации, сервис учебного контента и диагностики. OpenAPI 3.1, HTTPS, JWT/OIDC, миграции БД, наблюдаемость OpenTelemetry. Для учебного контента: Markdown/MDX-подобная безопасная схема + JSON для упражнений, AST-проверки, примеров и тестов. Не исполнять произвольный HTML/JS из уроков.

**Структура монорепозитория:** `apps/devcat_flutter/`, `services/api/`, `services/runner/`, `services/content/`, `packages/course_schema/`, `packages/theme_tokens/`, `packages/cat_assets/`, `content/{cpp,c,csharp,python,java,javascript,go,sql,git}/`, `infra/`, `docs/`, `tests/`, `.github/workflows/`.

**ОС и окна:** на Windows/macOS/Linux — системное окно с аккуратными скруглёнными углами там, где это допускает оконный менеджер; не пытаться принудительно обрезать нативную рамку, если это ломает управление, resize, snap, fullscreen или accessibility. Нативные кнопки управления окном, drag region, минимальный размер, масштабирование DPI, восстановление геометрии. На Android — edge-to-edge, системные inset, жестовая навигация, поддержка планшетов и внешней клавиатуры.

## 3. Первый запуск, аккаунт и выбор обучения

Онбординг (пропускаемый, с возможностью изменения позже): приветствие кота → язык UI → выбор одного или нескольких направлений (C, C++, C#, Python, Java, JavaScript, Go, SQL, Git/GitHub) → уровень (с нуля/базовый/опытный) → цель (учёба/работа/проект/собеседование) → доступное время → предпочитаемый формат (теория/практика/смешанный) → тема (системная/светлая/тёмная/своя) → предложение импортировать существующий проект → необязательная регистрация.

После входа: две **главные учебные вкладки** «Языки» и «Git/GitHub»; внутри «Языки» переключатель активного курса. Отдельная вкладка «IDE»; дополнительно «Главная», «Справочник», «Прогресс», «Настройки». На мобильном — bottom navigation для основных разделов и вложенная навигация; на ПК — navigation rail/sidebar. Переключение курсов не сбрасывает прогресс; несколько параллельных треков; персональная учебная дорожная карта и переоценка навыков; экспорт прогресса.

Профиль гостя: локальные курсы, IDE и прогресс без регистрации. Аккаунт: синхронизация с явным согласием, безопасное объединение прогресса и разрешение конфликтов. Удаление аккаунта и экспорт данных.

## 4. Дизайн: настоящий Material Design 3 / Material You

Ориентир — визуальные и поведенческие паттерны приложений Google Pixel, **без копирования чужих товарных знаков или закрытых ассетов**. Использовать актуальные Material 3 компоненты, tonal surfaces, dynamic color на поддерживаемом Android, типографику, состояния pressed/hover/focus, adaptive layouts, понятную иерархию, ripple, elevation, выразительные формы и корректные отступы. Никакого принудительного фиолетового: системная палитра по умолчанию; альтернативные палитры — голубая, зелёная, оранжевая, нейтральная, розовая, OLED и пользовательская.

Полный редактор темы: `primary`, `onPrimary`, `primaryContainer`, `secondary`, `tertiary`, `surface`, `surfaceContainer*`, `background`, `onSurface`, `outline`, `error`, `success`, `warning`, цвета редактора, диалогов кота, выделений, синтаксиса и терминала. Выбор HEX/RGB/HSL, color picker, история цветов, контрастный предпросмотр, сохранение пресетов, импорт/экспорт JSON, сброс. Два режима: «Автопалитра Material You» и «Ручная настройка каждого токена». Проверять WCAG-контраст, не заменять цвета пользователя молча; предупреждать и предлагать исправление.

Настраиваемые скругления, плотность, размер шрифта, редакторский моноширинный шрифт, масштаб UI, анимации, интенсивность, reduced motion. Весь UI использует design tokens; без захардкоженных цветов. Изменения применяются мгновенно и сохраняются. Поддержка светлой/тёмной/системной темы и high contrast.

**Анимации:** переходы экранов 180–320 мс, микроинтеракции 100–220 мс, кот 6–12 fps для пиксельной анимации (без сглаживания пикселей), прогресс, загрузка, смена темы, раскрытие объяснений, подсветка строки ошибки. Важнее плавность, чем количество эффектов; цель 60 fps на поддерживаемых устройствах; снижать нагрузку на слабых устройствах; уважать reduced motion.

## 5. Кот-наставник: строго по исходному изображению

**Единственный канонический референс — `DevCat_assets/cat_original.jpg`**, приложенный пользователем. Сохранить чёрный сплошной пиксельный силуэт, две острые ушки с белыми внутренними участками, маленькие горизонтальные белые глаза, вытянутый хвост слева, низкую горизонтальную форму и грубую ступенчатую геометрию. Не превращать в круглого мультяшного кота, не добавлять цветные глаза, нос, рот, усы или гладкие контуры. Допускаются маленькие внешние значки эмоций (звёздочки, вопрос, восклицание), но базовый силуэт неизменен.

Требуемые отдельные спрайты с прозрачным фоном, единым размером холста и целочисленным масштабированием nearest-neighbor: `idle_01..04`, `talk_01..06`, `blink_01..03`, `happy_01..04`, `sad_01..04`, `confused_01..04`, `error_01..04`, `thinking_01..06`, `success_01..06`, `sleep_01..04`, `point_01..04`, `wave_01..04`, `loading_01..06`. Обязательны spritesheet PNG + atlas JSON с координатами кадров, длительностями и anchor point; допускается Aseprite исходник, если лицензия позволяет. **Существующие концепт-изображения — только визуальные примеры, не готовые кадры анимации.** При отсутствии реальных спрайтов реализовать временный idle на основе исходного фото с явным TODO и без заявления, что набор готов.

Диалог кота: текст печатается постепенно, синхронное переключение кадров «говорит», пауза/пропуск печати, история реплик, возможность отключить кота, размер и расположение. Кот объясняет ошибки дружелюбно, но точно, никогда не выдаёт догадки за подтверждённую диагностику. Состояния: приветствие, урок, подсказка, ожидание, компиляция, успех, ошибка, достижение, offline. Контекстные сообщения локализуемы; ограничить частоту появления, не перекрывать редактор и системные элементы.

## 6. Учебный движок

Единая структура: **направление → версия языка/инструмента → трек → модуль → урок → блок теории → пример → мини-проверка → практика → тесты → разбор → повторение**. Каждый урок: `id`, `slug`, язык, версия, предпосылки, цели, теория, объяснение терминов, 2–5 примеров, типичные ошибки, ссылки на первоисточники, задания нескольких сложностей, эталонные решения (закрытые до выполнения), тесты, рубрика оценки, теги, время, дата последней проверки и автор/ревьюер.

Типы практики: выбор ответа; восстановить порядок строк; заполнить пропуск; исправить баг; предсказать вывод; написать функцию; полноценный проект; SQL-запрос к данным; командная строка; Git-сценарий; code review; тестирование; дебаг; рефакторинг; оптимизация; объяснение чужого кода. У каждого задания проверяемые критерии; не оценивать только совпадение текста ответа.

Три уровня подсказок: концептуальный намёк → указание места/причины → частичный пример. Решение целиком только по запросу/после попыток; режим «без спойлеров». Разбор ошибок: категория (синтаксис/типы/сборка/рантайм/логика/стиль/безопасность), файл и строка, точная диагностика компилятора/рантайма, человеческое объяснение, минимальный контрпример, направление исправления, повторный запуск. Если уверенности недостаточно — «возможная причина» и предложить диагностические шаги. Различать неверный ответ и баг тестирующей системы.

Автопроверка: unit tests, property-based tests, сравнение stdout с нормализацией, проверка SQL-результатов, AST/static analysis там, где уместно, ограничения времени/памяти. Скрытые тесты не отправлять на клиент. Учитывать численную погрешность, порядок строк при неупорядоченных результатах, исключения и версии компиляторов. Предусмотреть ручное сообщение о некорректном тесте.

Повторение: интервальные повторения, карточки терминов, персональные слабые места, итоговые проекты, входное тестирование, достижения, XP, серии дней с возможностью отключения, статистика по навыкам. Не штрафовать за пропуск дня агрессивными механиками.

## 7. Полное покрытие знаний: политика контента

Вести **матрицу покрытия** для каждого языка и версии: лексика, грамматика, семантика, типы, выражения, операторы, объявления, области видимости, память, исключения, параллелизм, модули, сборка, стандартная библиотека, tooling, тесты, безопасность, производительность, распространённые ошибки, платформенные особенности, миграции и изменения между версиями. Справочник содержит отдельные статьи по каждому синтаксическому элементу и API стандартной библиотеки, включая примеры, edge cases, версию введения/устаревания и ссылки на официальную документацию.

**Источники:** официальные спецификации, reference manuals, language proposals/notes, официальная документация компиляторов и стандартных библиотек, документация Git/GitHub, официальные guides и лицензируемые учебные материалы. Сохранять URL, версию, дату проверки, условия лицензии, хеш/источник, редактора и статус. Не копировать массово защищённые учебники или документацию без лицензии; использовать ссылки, собственные объяснения, открыто лицензированные материалы с атрибуцией. Не обещать «все базы данных мира» — создать расширяемый репозиторий знаний с прозрачными источниками.

Контент проходит: импорт/авторство → schema validation → lint → сборка примеров → выполнение тестов на нужных версиях → экспертное ревью → публикация → периодическая перепроверка. Версионировать задания и сохранять историю оценивания. Обновлять при релизах языков, toolchain, библиотек и при выявленных ошибках. Метрики: процент заполнения матрицы по разделам, процент проверенных примеров, возраст последней проверки, число подтверждённых ошибок контента, доля упражнений с тестами. **Не генерировать фиктивные «полные курсы» с пустыми заголовками.**

### 8.9 Git и GitHub — отдельная главная вкладка

**Теория:** различие Git и GitHub; репозиторий, working tree, staging/index, commit, HEAD, branches, tags, remotes, history; установка и настройка; `.gitignore`, `.gitattributes`, `README`, лицензии; `init/status/add/commit/log/diff/show/restore/reset/revert/branch/switch/checkout/merge/rebase/cherry-pick/stash/fetch/pull/push/clone/tag`; конфликты, reflog, bisect; SSH keys и HTTPS tokens; GitHub аккаунт, репозитории, public/private, README, Issues, Projects, Discussions, Pull Requests, review, forks, Releases, Actions/CI, branch protection/rulesets, CODEOWNERS, Dependabot, GitHub Pages, безопасность и секреты, Git LFS, submodules, GitHub CLI, работа в команде, GitHub API, GitHub-hosted runners и лимиты, подключение к удалённым серверам по SSH, развёртывание учебного проекта.

**Практика по возрастанию:**
1. Создать локальную папку, `git init`, `README.md`, первый `git add` и `git commit`; проверить `git log`.
2. Изменить файл, изучить `git diff`, selective staging, сделать осмысленный коммит.
3. Создать ветку, изменить код, объединить ветки, разрешить учебный конфликт.
4. Создать GitHub-репозиторий через браузер или GitHub CLI, настроить `remote`, выполнить `push`.
5. `clone`, `fetch`, `pull`, создать Pull Request, провести review и merge.
6. Сделать `.gitignore`, не добавить секреты, восстановить случайно удалённый файл.
7. Написать workflow GitHub Actions для тестирования проекта; читать логи и исправлять ошибку.
8. Сгенерировать SSH-ключ локально, добавить **публичный** ключ в GitHub; не отправлять приватный ключ в DevCat.
9. Подключиться к собственному тестовому серверу по SSH, проверить fingerprint host key, выполнить безопасные команды, скопировать файл по SCP/SFTP; никаких чужих серверов.
10. Итог: опубликовать собственный проект, оформить README, лицензию, issues, PR, CI и релиз.

Для упражнений с Git — **виртуальный учебный репозиторий** в песочнице, поддерживающий настоящую семантику команд; проверять состояние `.git` и граф коммитов. Для GitHub API — отдельный режим подключения OAuth с минимальными scope и подтверждением перед публикацией/удалением. Учебные mock-сценарии не выдавать за реальные действия на GitHub. Инструкции по SSH: host verification, keys, permissions, agent, port forwarding только с разрешением и пояснением рисков. Не хранить пароли и приватные ключи в логах или учебном контенте.

## 10. Компиляция, интерпретация и запуск — обязательная реальная реализация

**Desktop:** обнаружение локальных toolchains, отображение версий, установка через официальные инструкции/управляемый установщик с согласием, выбор toolchain для workspace. C: Clang/GCC; C++: Clang/GCC (опционально MSVC на Windows при установленном Visual Studio Build Tools); C#: dotnet SDK; Java: JDK; Go: Go toolchain; Python: CPython; JS: Node.js; SQL: SQLite локально, PostgreSQL по подключению. Проверить лицензионные условия дистрибуции каждого инструмента; не распространять сторонние toolchains без проверки.

**Android:** полноценный C/C++/C#/Java/Go toolchain и отладка локально на любом телефоне не гарантируются из-за ABI, объёма, sandbox и ограничений ОС. Основной надёжный путь — **удалённый изолированный runner**; возможные локальные runtimes (например, SQLite, JS, ограниченный Python) — только после отдельного feasibility spike и проверок производительности/совместимости. Пользователь видит, где исполняется код, какие файлы отправляются и какие лимиты действуют.

**Runner API:** `POST /executions`, `GET /executions/{id}`, `GET /executions/{id}/events`, `DELETE /executions/{id}`, `POST /tests/run`, `GET /toolchains`; вход: язык, версия, список файлов, entrypoint, stdin, args, ограничения, идентификатор проекта, набор разрешённых зависимостей; выход: статус, stdout/stderr, exit code, diagnostics (file/range/severity/code), duration, memory, test cases, artifact refs. Статусы `queued/building/running/succeeded/failed/timed_out/cancelled`.

**Изоляция обязательна:** отдельный worker/VM или эквивалентная сильная изоляция для недоверенного кода, non-root, read-only base image, ephemeral filesystem, seccomp/AppArmor/SELinux по платформе, ограничения CPU/RAM/PIDs/disk/time, network deny-by-default, no host mounts, запрет Docker socket, rate limiting, quota, anti-abuse, очистка временных файлов, аудит и redaction секретов. Одного контейнера без hardening недостаточно для безопасного multi-tenant выполнения. Отдельная очередь, таймауты компиляции и запуска, лимиты stdout, отмена и уборка процессов. При сетевом доступе — явный allowlist и пользовательское подтверждение.

**Примеры реальных команд (на ПК):**
```sh
clang -std=c17 -Wall -Wextra main.c -o app
clang++ -std=c++20 -Wall -Wextra main.cpp -o app
dotnet run --project ./App.csproj
javac Main.java && java Main
go run .
python main.py
node main.js
sqlite3 lesson.db < query.sql
```
Команды приведены как ориентиры; в продукте использовать безопасный запуск процессов без shell interpolation, корректную обработку путей, платформ и аргументов. Для компиляции C/C++ — отдельные профили debug/release, ASan/UBSan там, где доступны; показывать версию стандарта и toolchain.

## 11. Объяснение ошибок и AI-помощник

Приоритет: структурированные сообщения компилятора → сопоставление с картой урока/известных ошибок → детерминированные рекомендации → опциональный LLM-разбор. LLM не заменяет компилятор или тесты. Для каждой ошибки: «что произошло», «почему», «где», «как проверить», «как исправить», «как избежать». Привязка к конкретной версии языка и компилятора. Для ошибок логики — тест-кейсы, трассировка, expected/actual и возможные причины. Для SQL — планы запросов и сообщения СУБД. Для Git — состояние репозитория, конфликтные файлы, безопасные варианты действий.

Опциональный AI: явное согласие на передачу кода третьей стороне, редактирование/маскирование секретов, кнопка «не отправлять этот проект», лимиты и стоимость, хранение истории по настройкам приватности, fallback без AI. Запрет выдавать неподтверждённые исправления за гарантированно верные. Приоритет педагогики: сначала подсказка, потом подробный разбор.

## 16. Примеры контента, который должен быть реально создан в MVP

**C++ / Переменные.** Теория: объявление `int age = 20;`, различие типа и значения, вывод `std::cout`, `#include <iostream>`. Практика: запросить имя и возраст, вывести строку; тесты: обычный ввод, пустое имя (оговорить формат), граничные значения. Диагностика: отсутствующая `;`, `std::`/namespace, неверный тип.

**Python / Циклы.** Теория `for`, `range`, границы последовательности, indentation. Практика: сумма чисел от 1 до N; тесты N=1, N=10, N=0 по оговорённому контракту. Ошибки: off-by-one, неверный отступ.

**SQL / JOIN.** Теория PK/FK, INNER/LEFT JOIN, NULL. Практика: вывести всех покупателей и число заказов, включая покупателей без заказов; проверить результат на синтетических таблицах и независимом наборе тестовых данных.

**Git / Первый коммит.** Теория working tree → index → repository, commit как снимок состояния, назначение сообщения. Практика в изолированном репозитории: `git init`, создать README, `git add README.md`, `git commit -m "Initial commit"`, `git log --oneline`. Проверка: наличие коммита и README в дереве; отдельная подсказка при ошибке `user.name/user.email`. GitHub-публикация — следующий урок, не обязательна для первого коммита.

Для **каждого** урока обеспечить минимум одну задачу, объяснения двух типичных ошибок и рабочие тесты. Расширенные курсы должны содержать большие проекты, ревью и диагностику; не заменять это сгенерированными одинаковыми упражнениями.

## 21. Инструкции Codex по выполнению

1. Сначала прочитать **весь** документ и `DevCat_assets/cat_original.jpg`; составить карту требований и список технических рисков.
2. Создать `IMPLEMENTATION_PLAN.md` с фазами, задачами, зависимостями, критериями готовности и чек-листом по каждому направлению.
3. Не пытаться за один запрос реализовать весь продукт; выполнять вертикальные срезы end-to-end с работающими тестами.
4. Не генерировать пустые уроки, mock-runner или UI-заглушки под видом завершённых функций. Неисполненные пункты явно маркировать `NOT_IMPLEMENTED` и описывать в плане.
5. Для каждой функции указывать desktop/Android поддержку отдельно и реальные ограничения.
6. Выбирать существующие безопасные toolchains и language servers, документировать лицензии и версии.
7. При создании контента указывать официальные источники, версии, редакторскую проверку и тесты примеров.
8. Сохранять пиксельный стиль кота, не менять его геометрию и не применять сглаживание.
9. Писать чистый модульный код, соблюдать доступность, безопасность, тестируемость и возможность замены компонентов.
10. После каждого этапа запускать тесты, фиксировать результаты и давать точные команды запуска.

## 22. Явные исключения и ограничения

- DevCat **не обязан создавать новый компилятор с нуля**: это отдельная многолетняя научно-инженерная задача. Обязателен собственный интеграционный слой компиляции и исполнения.
- Полная совместимость со всеми расширениями VS Code, всеми библиотеками, всеми версиями языков и всеми платформенными API не гарантируется; поддержка определяется опубликованной матрицей.
- GitHub, package registries, серверные подключения и remote runner требуют сети, прав и соблюдения квот; нельзя выдавать их за офлайн-функции.
- Пользовательские проекты и SSH-ключи никогда не должны попадать в обучающие датасеты или AI-сервисы без отдельного согласия.
- Источники знаний и документация обновляются постоянно; каждое утверждение о поддержке привязано к версии.
