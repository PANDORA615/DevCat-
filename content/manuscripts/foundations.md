# basics
## Исходный текст, запуск и наблюдаемый результат
У программы есть несколько разных представлений. Исходный текст читаем мы и инструменты разработки. Компилятор переводит подходящую часть этого текста в машинные инструкции или байткод. Среда исполнения создаёт процесс, выделяет ему память и соединяет стандартные потоки. Наконец, конкретный запуск получает конкретный ввод и производит вывод. Изменение файла после начала запуска обычно не меняет уже выполняющийся процесс: чтобы проверить правку, программу запускают заново.

Разделяй три вопроса: удалось ли подготовить программу, удалось ли её выполнить и соответствует ли результат условию. Синтаксически корректная программа вполне может вычислять неверную сумму. Программа, которая правильно считает сумму, может нарушить протокол лишним приглашением ввода. А отсутствие компилятора вообще не является свойством твоего алгоритма. Именно поэтому сначала читают сообщение среды, затем код завершения и фактический вывод, а уже после сравнивают ответ с контрактом.

Стандартный ввод — поток символов, а не волшебная переменная с готовым числом. Программа должна прочитать эти символы, определить их смысл и при необходимости выполнить преобразование. Стандартный вывод предназначен для результата. Диагностика обычно идёт в отдельный поток ошибок: при отладке это помогает увидеть причину сбоя, не испортив машинно проверяемый ответ.
## Полный разбор первой вычислительной задачи
Пусть доставка стоит 3 денежные единицы за оформление и ещё 4 за каждый килограмм. Обозначим массу через n. Из условия получается функция f(n) = 4n + 3, где n — целое от 0 до 1000. Здесь уже определены допустимый ввод, вычисление и тип ответа. Для n = 5 сначала получаем стоимость массы 20, затем добавляем оформление и выводим 23. Для n = 0 переменная часть исчезает, но оформление остаётся: ответ 3. Это хороший тест против ошибочной формулы 4(n + 3).

Прежде чем писать код, составь три строки псевдокода: прочитать n; вычислить 4n + 3; напечатать результат. После реализации проверь их соответствие настоящим операциям. Переменную результата можно выделить отдельно, чтобы проследить промежуточное состояние, а затем при желании сократить выражение. Важно сохранить смысл, а не добиться минимального числа строк.
## Эксперимент и границы применимости
Для ручной проверки используй 0, 1 и 1000: они дают 3, 7 и 4003. Затем намеренно замени плюс на умножение и убедись, что набор обнаруживает ошибку. Отдельно попробуй передать буквы вместо числа. Если условие гарантирует корректный ввод, учебное решение может полагаться на эту гарантию; интерактивный калькулятор должен сообщать об ошибке преобразования. Это два разных контракта, и их нельзя незаметно смешивать.

Самостоятельное усложнение: ввести бесплатную доставку при массе от 20. Сначала уточни, исчезает ли только плата за килограммы или вся стоимость. Такая неоднозначность не решается выбором оператора: её нужно устранить в постановке задачи. Умение превратить бытовое требование в точный контракт начинается уже с первой программы.

# values
## Тип задаёт допустимые действия
Значение нужно рассматривать вместе с его типом и единицей измерения. Число 199 может означать рубли, копейки, количество предметов или идентификатор. Машина не отличит эти смыслы сама, поэтому имена и контракт должны их передавать. Если цена записана в копейках, три товара по 199 копеек стоят 597 копеек. Переменная priceCents понятнее абстрактной x, даже когда обе имеют один числовой тип.

Целое число подходит для счётчика, индекса и точной суммы в минимальных денежных единицах. Число с плавающей точкой приближённо представляет широкий диапазон величин. Это полезно для измерений, но десятичная дробь 0,1 обычно не имеет точного конечного двоичного представления. Поэтому равенство двух результатов вычислений с дробями не всегда проверяют обычным сравнением, а денежные расчёты требуют заранее выбранной модели округления.

Строка «42» и число 42 описывают разный способ работы с данными: строковые операции соединяют и исследуют символы, арифметические — числа. Преобразование не должно происходить случайно. В языке с неявными преобразованиями сначала выясни его правила; в языке с явными преобразованиями проверь, может ли операция завершиться ошибкой или потерять информацию.
## Проверка диапазона до выбора представления
Предположим, в заказе до миллиона товаров, каждый ценой до миллиона минимальных денежных единиц. Количество и цена по отдельности помещаются в обычное 32-битное знаковое целое, но их произведение может достигать 10¹². Выбирать тип нужно по промежуточным результатам, а не только по отдельным входам. В C/C++ знаковое переполнение недопустимо; в Java результат переполнения целого определён, но математический ответ всё равно будет неверен. В Python целые растут по мере необходимости, однако на их обработку расходуются память и время.

Сравни ещё две величины: номер заказа и число заказов. К номеру обычно нельзя осмысленно прибавлять другой номер, хотя технический тип может это позволить. При проектировании больших программ такие различия закрепляют отдельными типами или проверяемыми моделями.
## Три полезных исследования
Проверь деление 5 на 2, преобразование строки «005» в число и сравнение очень близких дробей. Запиши для каждого опыта ожидаемый тип и результат до запуска. Затем восстанови обратное преобразование: число 5 уже не хранит информацию о двух ведущих нулях исходного текста. Если они значимы, например в почтовом индексе, данные с самого начала должны оставаться строкой.

Усложнение: придумай представление температуры, денег и номера банковской карты. Для каждого объясни диапазон, точность, допустимые операции и формат хранения. Универсального «лучшего числового типа» нет: подходящее представление следует из требований.

# variables
## Состояние программы меняется по правилам
Переменная позволяет связать имя с текущим значением или объектом в соответствии с моделью языка. Присваивание не является математическим равенством на все времена. Операция balance = balance + 25 сначала читает старое значение справа, вычисляет новое и только затем обновляет состояние слева. Если до операции было 100, после неё будет 125. Следующее вычитание 40 даёт 85; первоначальное значение не восстанавливается автоматически.

Полезно отличать значение, имя и объект. При присваивании простого числа обычно достаточно рассуждать о его текущем значении. С коллекциями появляется дополнительный вопрос: два имени могут обращаться к одному изменяемому объекту. Копирование имени не обязано создавать копию всех данных. Правила C, C++, Python, Java, C# и JavaScript различаются, поэтому отдельно проверь, где копируется значение, а где сохраняется общая ссылка.

Изменяемое состояние упрощает накопление результата, но усложняет объяснение программы. Чем больше мест могут изменить одну переменную, тем труднее восстановить причину значения. Поэтому ограничивай область видимости, выбирай понятные имена и используй неизменяемые привязки там, где повторное присваивание не нужно.
## Таблица выполнения и обмен значений
Проследи баланс: старт 100; пополнение 25; покупка 40; итог 85. Для каждой строки укажи старое значение, действие и новое значение. Теперь поменяй порядок пополнения и покупки. Итоговая сумма останется той же, но проверка «хватает ли денег прямо сейчас» может дать другой результат. Это показывает различие между конечным арифметическим выражением и последовательностью операций с ограничениями.

Для обмена a = 2 и b = 7 нельзя последовательно написать a = b; b = a: после первой строки первоначальная двойка уже потеряна. Нужна временная переменная или предусмотренная языком операция обмена. После корректного обмена a равно 7, b равно 2. Пошаговая таблица объясняет причину лучше запоминания готового трюка.
## Проверяемые свойства состояния
Определи инвариант счёта: баланс неотрицателен. Операция покупки сначала проверяет достаточность средств и только затем меняет значение. При отказе баланс должен остаться прежним. Проверь покупку дешевле баланса, ровно на всю сумму и дороже баланса. Для последнего случая недостаточно напечатать сообщение об ошибке, если сама переменная уже стала отрицательной.

Усложнение: перевести деньги между двумя счетами. Сумма балансов до и после успешного перевода должна совпадать. При любой ошибке оба счёта должны сохранить исходные значения. Так простое присваивание постепенно приводит к идеям инварианта и атомарной операции.

# expressions
## Дерево выражения и порядок вычислений
Выражение состоит из операндов и операций. Приоритет помогает понять группировку, но не заменяет знание порядка вычисления и правил типов конкретного языка. В записи 2 + 3 × 4 умножение образует внутренний узел дерева, поэтому ответ 14. Скобки в (2 + 3) × 4 меняют дерево и дают 20. Они полезны и тогда, когда приоритет уже известен: читателю легче увидеть замысел.

При целочисленном делении дробная часть не сохраняется. При этом правила отрицательного деления и остатка различаются: Python использует округление частного вниз, тогда как C17, C++, Java и C# для обычных знаковых целых отбрасывают дробную часть к нулю. Нельзя переносить формулу с отрицательными значениями между языками, не проверив это различие. Деление на ноль требует отдельной обработки.

Оператор, который выглядит кратко, может иметь побочный эффект. Изменение переменной внутри большого выражения делает трассировку труднее, а в C/C++ некоторые сочетания изменений и чтения одного объекта недопустимы. Безопаснее сначала получить нужные промежуточные значения, а затем вычислить результат в ясном порядке.
## Перевод секунд в минуты и остаток
Для 135 секунд полные минуты равны 135 div 60 = 2, оставшиеся секунды — 135 mod 60 = 15. Проверка результата: 2 × 60 + 15 = 135, причём остаток лежит от 0 до 59. Это не два независимых числа, а разложение исходной величины. Для 59 секунд ответ 0 минут 59 секунд; для 60 — 1 и 0; для 0 — 0 и 0.

Теперь требуется округлить положительную длительность вверх до полных минут. Для неотрицательного n часто используют (n + 59) div 60. Объясни, почему прибавляется 59, и отдельно проверь переполнение n + 59. В ограниченном целочисленном типе безопаснее иногда использовать n div 60 плюс единицу, когда остаток ненулевой.
## Контрпримеры вместо угадывания
Испытай формулу на значениях вокруг границы: 59, 60 и 61. Если все проверки были только на больших круглых числах, ошибка округления могла остаться незаметной. Для среднего двух больших целых проверь не только итоговый диапазон, но и переполнение суммы перед делением. Для процентов уточни, где округляется результат: после каждой позиции или после общей суммы.

Самостоятельная работа: рассчитать количество коробок по вместимости k. Определи, допускаются ли ноль предметов и нулевая вместимость. Доказательство формулы должно использовать эти ограничения, а не предположение, что ввод всегда удобен.

# input
## Внешние символы ещё не являются данными нужного типа
Ввод имеет минимум три уровня проверки. Сначала определяется, удалось ли прочитать текст вообще: поток может закончиться раньше времени. Затем проверяется синтаксис числа, даты или другой записи. После успешного преобразования проверяются предметные ограничения, например возраст от 0 до 150. Строка «999» является корректной записью целого, но не допустимым возрастом в таком контракте.

Выбор способа чтения зависит от формата. Чтение отдельного слова обычно останавливается на пробельном символе; чтение строки сохраняет внутренние пробелы. Если имя «Анна Петрова» должно целиком попадать в одну переменную, его нельзя незаметно разбивать на два независимых токена. Смешивание разных способов ввода требует внимания к оставшемуся разделителю строки.

Конец файла отличается от пустой строки. Пустая строка может быть допустимым значением, например отсутствующим комментарием; EOF означает, что данных больше нет. Интерактивная программа может предложить повторить ввод. В автоматической задаче обычно заранее задано, как именно обрабатывать неправильные данные: нельзя самовольно менять протокол ответа.
## Разбор имени и возраста
Контракт: первая строка содержит имя целиком, вторая — целый возраст. Для ввода «Анна Петрова» и 20 нужно получить две величины: строку с пробелом и число 20. Сначала читаем имя строкой. Затем читаем возраст, преобразуем и проверяем диапазон. Если имя может быть пустым, удалять пустые строки перед чтением нельзя: тогда возраст случайно станет именем.

Построй таблицу проверки: обычное имя и 20; пустое имя и 0; имя с пробелами и 150; корректное имя и буквы вместо возраста; отсутствие второй строки. Каждый пример проверяет отдельное решение в коде. Чтение числа без проверки успешности особенно опасно в языках, где после неуспеха переменная может сохранить прежнее или недопустимое значение.
## Отделение разбора от вычислений
Удобная архитектура состоит из функции разбора, вычислительного ядра и форматирования ответа. Ядро получает уже проверенные значения и не должно одновременно спрашивать их у пользователя. Тогда его можно тестировать без консоли, а одинаковое правило использовать в CLI и интерфейсе приложения.

Усложнение: прочитать список цен с указанием количества элементов в первой строке. Проверь отрицательное количество, слишком большое значение, нехватку элементов и лишние символы в числах. Сообщение об ошибке должно указывать на нарушение контракта, а не завершаться неясным исключением из глубины вычисления.

# booleans
## Условие — высказывание с определённой семантикой
Булево выражение отвечает на вопрос о данных, а не описывает само действие. Условие age >= 18 проверяет возраст; оно ничего не покупает и не разрешает, пока программа не использует результат. Удобно сначала сформулировать требование человеческим языком, затем назвать отдельные предикаты и лишь после соединить их.

Если доступ разрешён совершеннолетнему владельцу билета, нужны оба условия: достаточный возраст И наличие билета. Если разрешён владелец билета ИЛИ сотрудник, достаточно одного. Изобрази все сочетания двух булевых признаков: false/false, false/true, true/false, true/true. Такая таблица обнаруживает путаницу между «хотя бы одно» и «ровно одно».

Короткое замыкание означает, что некоторые логические операции не вычисляют правую часть, когда результат уже определён левой. Это позволяет сначала проверить наличие объекта, а затем обращаться к его полю. Но конкретные операторы различаются: побитовое И не является универсальной заменой логического И, а в Python и JavaScript некоторые логические выражения возвращают один из операндов, не обязательно булево значение.
## Проектирование диапазона
Чтобы число x лежало между 10 и 20 включительно, нужны условия x >= 10 И x <= 20. Проверка через ИЛИ ошибочна: для x = 100 правая половина ложна, но левая истинна, поэтому всё выражение становится истинным. Для x = 0 срабатывает другая половина. Контрпример помогает увидеть, что неправильное условие пропускает фактически все числа.

Отрицание принадлежности диапазону можно записать как НЕ(10 <= x <= 20 в подходящем синтаксисе) либо как x < 10 ИЛИ x > 20. Это применение закона де Моргана. В большинстве рассматриваемых языков математическую цепочку сравнений нужно раскрывать; Python поддерживает цепочки с собственной семантикой.
## Безопасность составного условия
Пусть нужно проверить, что список непустой и его первый элемент положителен. Сначала проверяется непустота. Перестановка частей может привести к обращению по несуществующему индексу. По той же причине важно не прятать изменение состояния в условие, если порядок и число вызовов влияют на результат.

Для каждого условия подготовь значения непосредственно до границы, на границе и после неё. Возраст 17, 18 и 19 позволяет проверить порог лучше, чем три случайных больших возраста. Дополнительно проверь каждую комбинацию остальных признаков, чтобы одна всегда истинная часть не скрыла ошибку другой.

# branches
## Каждая ветвь должна соответствовать области входов
Цепочка if/else if/else выбирает первую подходящую ветвь. Несколько отдельных if могут выполнить несколько действий. Поэтому сначала реши, являются ли случаи взаимоисключающими. Классификация числа как отрицательного, нуля или положительного требует ровно одного ответа; независимые уведомления о скидке и бонусе могут сработать одновременно.

Полезно разбить допустимое множество входов на непересекающиеся области. У каждой области должно быть объяснение, а объединение областей должно покрывать все допустимые значения. Если остался вход, для которого не подходит ни одна ветвь, программа может не вывести результата. Если один вход попал сразу в несколько независимых ветвей, возможны противоречащие сообщения.

Порядок проверок особенно важен для вложенных порогов. Если сначала проверить сумму покупки >= 100, а затем через else if сумму >= 1000, второй случай никогда не будет достигнут. Крупные суммы уже удовлетворяют первому условию. Можно проверять от самого строгого порога к более мягкому или явно задавать непересекающиеся интервалы.
## Разбор ступенчатой скидки
Пусть при сумме меньше 100 скидки нет, от 100 до 999 включительно скидка 5%, от 1000 — 10%. Получаются области [0,100), [100,1000), [1000,+∞). Проверь 99, 100, 999 и 1000. В каждом случае выпиши выбранную ветвь и ставку. Если сумма задана в копейках, границы тоже должны быть в копейках.

Теперь отдели выбор ставки от вычисления суммы. Сначала ветвление устанавливает ставку, затем общая формула вычисляет результат. Это уменьшает дублирование. Но для точного денежного результата ещё нужно определить округление, поэтому логическая правильность ветвей не решает автоматически вопрос числовой точности.
## Уменьшение вложенности
Сложные проверки удобнее делать по этапам. Сначала отклоняется недопустимый вход; дальше основная ветвь работает с уже выполненными предусловиями. Ранний выход может сделать код яснее, если не скрывает необходимые операции освобождения ресурса. Не считай количество вложенных блоков целью само по себе: задача — видеть контракт каждого пути.

Усложнение: добавить промокод, который нельзя сочетать со ступенчатой скидкой. Составь таблицу вариантов до написания кода и уточни, выбирается ли более выгодная скидка или приоритет имеет промокод. Неоднозначное правило нельзя исправить дополнительным else без решения на уровне требования.

# loops
## Цикл связывает начальное состояние, шаг и завершение
Правильный цикл отвечает на четыре вопроса: с чего начинается состояние, когда разрешено продолжение, как меняются данные и почему выполнение заканчивается. Накопитель суммы начинается с нуля, произведения — с единицы. Начальное значение выбирается по смыслу операции, а не по привычке использовать одно и то же число.

Инвариант — утверждение, которое верно перед началом очередного шага. Для суммы от 1 до n перед обработкой i накопитель содержит сумму уже обработанных чисел от 1 до i−1. Тело добавляет i и тем самым подготавливает инвариант следующего шага. После выхода обработаны все числа до n, поэтому накопитель соответствует требуемому ответу. Это маленькое доказательство, а не отдельная магическая техника для сложных задач.

У завершения тоже должна быть причина. В счётном цикле расстояние до верхней границы уменьшается; при чтении файла ожидается конец потока; при поиске состояние должно приближаться к результату или исчерпанию вариантов. Изменение не той переменной, пропуск шага после continue или сохранение прежнего условия способны сделать цикл бесконечным.
## Подробная трассировка суммы
Для n = 4 стартуем с total = 0. После i = 1 получаем 1, после 2 — 3, после 3 — 6, после 4 — 10. Если верхняя граница исключает 4, получится 6. Если total обнуляется внутри тела, останется только последнее значение 4. Если i увеличивается до прибавления, набор слагаемых сдвинется. У каждой ошибки есть отдельный наблюдаемый симптом.

Для n = 0 тело не должно выполняться, а ответом остаётся нейтральный элемент суммы — ноль. Этот тест одновременно проверяет корректность начального состояния и отсутствие лишней итерации. Для больших n оцени диапазон суммы: даже если n помещается в тип, накопитель может потребовать более широкого представления.
## Выбор модели обхода
Когда нужен каждый элемент коллекции, прямой обход часто понятнее индексов. Индексы нужны, если важна позиция или соседние элементы. Цикл while подходит, когда количество шагов заранее неизвестно, но условие завершения можно описать. Преобразуй один вид цикла в другой и проверь, сохранились ли начальное состояние, условие и шаг.

Усложнение: вычислить отдельно суммы чётных и нечётных чисел. Сначала опиши два инварианта, затем выбери один обход вместо двух. После выполнения их сумма должна равняться общей сумме: это полезное независимое свойство для проверки.

# nested
## Два измерения означают два независимых состояния
Во вложенном цикле один шаг внешнего цикла запускает полный предусмотренный обход внутреннего. Если строки идут от 0 до 1, а столбцы от 0 до 2, будут посещены пары (0,0), (0,1), (0,2), (1,0), (1,1), (1,2). Внешняя переменная меняется только после завершения внутренней последовательности. Это модель сетки, таблицы и перебора сочетаний.

Внутренний счётчик должен получать начальное значение для каждой новой строки. Если сохранить его после первого обхода и не сбросить, последующие строки могут остаться необработанными. Аналогично накопитель суммы строки создают внутри внешнего цикла, а сумму всей таблицы — до обоих циклов. Место объявления отражает время жизни нужного промежуточного результата.

Число шагов определяется допустимыми парами индексов. Для прямоугольника n × m оно равно nm. Для всех пар разных позиций с i < j получится n(n−1)/2. Оба алгоритма могут содержать два цикла, но второй не обязан повторно рассматривать обратные пары. Сначала определи множество нужных сочетаний, а затем запиши границы.
## Разобранная задача о парах
Для массива [2,4,7] перечислим пары позиций i < j: (0,1), (0,2), (1,2). Их суммы равны 6, 9 и 11. Начало j = i + 1 одновременно исключает пару элемента с самим собой и повторное рассмотрение обратного порядка. Если вместо этого начать j с нуля, появятся лишние пары, включая диагональ.

Теперь нужно найти две позиции с суммой 9. Полный перебор найдёт (0,2). Досрочный выход только из внутреннего цикла не обязательно остановит внешний. Нужно явно выбрать стратегию: вернуть результат из функции, использовать признак нахождения или предусмотренный языком механизм. Проверяй, требуется ли первая пара, все пары или только факт существования.
## Когда полный перебор становится дорогим
Для n = 10 число пар невелико, для n = 100000 их уже около пяти миллиардов. Это повод изменить алгоритм, а не просто переписать for на while. Для поиска суммы можно использовать множество ранее просмотренных значений или сортировку и два указателя, если контракт допускает такие изменения.

Усложнение: вывести треугольную таблицу только для j <= i. Сначала нарисуй форму для трёх строк, затем вычисли ожидаемое число напечатанных элементов. Проверка количества часто обнаруживает неверную границу ещё до анализа всех значений.

# strings
## Символ, кодовая точка и байт — разные уровни
Текст хранится в некоторой кодировке. В UTF-8 одна кодовая точка занимает переменное число байтов. Видимый знак может состоять из нескольких кодовых точек, например буквы и комбинируемого ударения. Поэтому длина в байтах, число кодовых точек и число воспринимаемых пользователем знаков не обязаны совпадать.

C обычно работает с массивом байтов и завершающим нулём; std::string в C++ сам по себе тоже не выполняет полноценный анализ Unicode. Python str представляет последовательность кодовых точек с внутренним представлением среды. Java и JavaScript используют UTF-16-кодовые единицы для обычной индексации, а в Go строка содержит байты и обход range декодирует руны. Эти различия определяют, что именно означает индекс.

Неизменяемость строки означает, что операция создаёт новое значение, а не обязательно правит старый объект. Многократное присоединение маленьких фрагментов может потребовать лишних копий. Для больших объёмов выбирают построитель строки, буфер или объединение подготовленных частей. Но прежде чем оптимизировать, нужно определить, какой именно текст получается.
## Разбор счётчика цифр
Пусть требуется считать только ASCII-цифры от 0 до 9. Для строки «A10-Б2» ответ 3: подходят 1, 0 и 2. Буква Б в UTF-8 занимает больше одного байта, но это не меняет смысл задачи. Проверка «0 <= символ <= 9» должна быть записана в синтаксисе языка и применяться к корректному представлению символа.

Если задача требует все десятичные Unicode-цифры, такой ASCII-тест уже недостаточен. Если нужно числовое значение целой строки, подсчёт отдельных цифр вообще не является парсингом числа. Знак минус, пробелы, разделитель дробной части и экспонента требуют определённой грамматики.
## Условия корректной обработки текста
Проверь пустую строку, только буквы, только цифры, смешанный текст и кириллицу. Для C отдельно проверь размер буфера и место завершающего нуля; для всех языков — выбранную кодировку файла и консоли. Удаление пробелов по краям допустимо только тогда, когда эти пробелы не имеют значения по контракту.

Усложнение: нормализовать слова для частотного словаря. Уточни правила регистра, дефисов, апострофов и знаков пунктуации. Визуально похожие строки могут иметь разные последовательности Unicode, поэтому корректная нормализация требует явного решения, а не случайного удаления «непонятных» символов.

# arrays
## Индекс выражает позицию, а длина ограничивает доступ
Последовательность из n элементов обычно имеет допустимые индексы от 0 до n−1. Число n обозначает границу за последним элементом, а не ещё одну ячейку. Полуоткрытый диапазон [0,n) удобен тем, что его длина равна n−0 и пустая последовательность естественно задаётся n = 0.

Разделяй логическую длину и физическую ёмкость. Динамическая коллекция может хранить три элемента в буфере на восемь позиций. Пользовательский код имеет право обращаться только к существующим элементам, если интерфейс явно не предоставляет другое правило. В C длина массива часто передаётся отдельным параметром; в управляемых коллекциях она обычно доступна через свойство или функцию.

Вставка, удаление и расширение могут переместить элементы или заменить внутренний буфер. Сохранённый индекс не является долговременным идентификатором записи, а сохранённая ссылка на элемент может потерять допустимость в соответствии с правилами контейнера. Для объектов каталога лучше иметь отдельный устойчивый id.
## Максимум среди отрицательных значений
Для массива [−5,−2,−9] максимум равен −2. Если начать накопитель maximum с нуля, программа выдаст число, которого в данных даже нет. Для непустого массива начни с первого элемента и сравнивай остальные. После обработки префикса накопитель должен быть максимумом именно этого префикса.

Пустой массив требует отдельного контракта: вернуть отсутствие, сообщить ошибку или использовать специальный тип результата. Нельзя незаметно прочитать первый элемент до проверки длины. Для суммы пустого массива естественен ноль, но из этого не следует, что ноль является правильным максимумом.
## Изменение коллекции во время обхода
При удалении элемента следующие позиции часто сдвигаются. Если после удаления увеличить индекс обычным способом, можно пропустить новый элемент на той же позиции. Альтернативы: обход с конца, построение новой отфильтрованной коллекции или поддерживаемый контейнером способ удаления через итератор.

Усложнение: удалить все отрицательные значения, сохранив относительный порядок остальных, за линейное время и без второй полной копии массива. Поддерживай отдельные индексы чтения и записи. Докажи, что уже записанный префикс содержит ровно подходящие элементы обработанной части.

# functions
## Контракт важнее длины тела функции
Функция связывает имя операции, параметры, результат и допустимые побочные эффекты. Предусловие описывает допустимый вход; постусловие — обещание при успешном завершении. Если функция вычисляет сумму цифр неотрицательного целого, нужно отдельно решить, что делать с отрицательным значением и как трактовать ноль.

Параметр и аргумент — разные роли. Параметр объявлен в определении, аргумент передаётся в конкретном вызове. Способ передачи определяет, какие изменения видит вызывающий код. Даже передача ссылки по значению может позволять изменять общий объект, не позволяя заменить переменную вызывающего кода. Поэтому нельзя сводить различия всех языков к лозунгу «всё передаётся по ссылке».

Чистая вычислительная функция получает данные и возвращает результат без чтения консоли и изменения глобального состояния. Это не обязательное правило для всего приложения, но хороший способ выделить ядро. Одну и ту же операцию тогда можно вызвать из интерфейса, теста и командной строки.
## Сумма цифр числа 105
Сохраняем остаток от деления на 10 и прибавляем его к накопителю: сначала 5, затем 0, затем 1. После каждого шага целочисленное деление удаляет последнюю цифру. Состояния: (105,0), (10,5), (1,5), (0,6). Первое число — необработанная часть, второе — сумма уже извлечённых цифр. При нуле необработанных цифр цикл заканчивается.

Инвариант объясняет, почему нулевые цифры не нужно специально пропускать: их вклад равен нулю, но разряд всё равно обрабатывается. Исходное число можно сохранить, если оно нужно после вызова. Изменение локального параметра не обязано менять аргумент у вызывающего кода.
## Декомпозиция и повторное использование
Не создавай функцию только потому, что встретились три строки. Выделяй осмысленное действие с понятным именем и контрактом. Функция parseInput может отвечать за разбор, digitSum — за вычисление, formatResult — за представление. Каждую можно проверить отдельно, а их соединение — интеграционным тестом.

Усложнение: найти число с максимальной суммой цифр в массиве. Повторно используй вычислительную функцию и уточни правило равенства: первое подходящее число, наименьшее или все подходящие. Без этого два решения могут быть одинаково разумными и при этом выдавать разные ответы.

# scope
## Видимость имени не равна времени жизни объекта
Область видимости отвечает, где можно обратиться к имени. Время жизни отвечает, когда существует сам объект или ресурс. Эти границы часто похожи, но не обязаны совпадать. Объект может продолжать существовать после завершения функции, если его жизненный цикл поддерживает другая ссылка; локальный объект в C/C++ может прекратить существование, хотя сохранённый адрес ещё лежит в другой переменной.

Каждый вызов функции имеет собственное состояние локальных переменных. Два вызова cost с разными аргументами не должны случайно делить один промежуточный total, если это не предусмотрено контрактом. Глобальное состояние меняет эту модель: поведение может зависеть от предыдущих вызовов. Поэтому тест только одного запуска часто не обнаруживает дефект накопления.

Затенение происходит, когда внутреннее имя скрывает внешнее. Это не обязательно ошибка языка, но легко становится ошибкой замысла: программист рассчитывает изменить счётчик внешнего блока, а на деле создаёт новый. При чтении кода привязывай каждое использование имени к конкретному объявлению.
## Разбор локального вычисления и опасного адреса
Функция стоимости получает цену 199 и количество 3. Она вычисляет локальный total = 597 и возвращает значение. После выхода локальное имя исчезает, но возвращённое значение может сохраняться у вызывающего кода. Для обычного числового результата в этом нет проблемы.

Совсем другой случай — возврат адреса локального массива из C-функции. После завершения вызова массив больше не живёт, и обращение по сохранённому адресу недопустимо. В Python возврат созданного списка сохраняет объект через механизм ссылок, но не создаёт независимые копии для всех получателей. Эти ситуации похожи внешне и требуют разного объяснения.
## Проверки скрытого состояния
Вызови функцию дважды с одинаковыми аргументами и проверь оба результата. Затем поменяй порядок разных вызовов. Если функция обещает зависеть только от входа, результат не должен меняться из-за истории. Для изменяемого результата проверь, не получают ли два клиента один и тот же объект там, где ожидались независимые экземпляры.

Усложнение: реализовать счётчик обращений с явно описанным владельцем состояния. Сравни глобальную переменную, объект и замыкание там, где они доступны. Объясни, кто создаёт счётчик, сколько независимых счётчиков существует и когда их состояние перестаёт быть нужным.

# collections
## Структура данных выбирается по операциям
Последовательность сохраняет позиции и обычно порядок элементов. Множество отвечает на вопрос принадлежности и не хранит повторные вхождения как отдельные элементы. Словарь связывает ключ с ассоциированным значением. Один и тот же набор исходных данных можно представить по-разному, но цена и смысл операций изменятся.

Для частотного словаря ключом является слово, значением — число его вхождений. Для списка последних действий нужен порядок и возможность повторения. Для проверки уникальности номеров подходит множество, но если позже понадобится число повторов, простого множества уже недостаточно. Решение начинается с перечня нужных запросов, а не с привычки везде использовать один контейнер.

Хеш-таблица обычно обеспечивает ожидаемую быструю работу поиска, вставки и удаления при подходящей реализации. Это не означает гарантированное постоянное время для любой ситуации. Ключи должны подчиняться контракту равенства и хеширования; изменение значимых частей ключа после помещения в таблицу может нарушить поиск в некоторых языках и моделях.
## Подсчёт слов на конкретном входе
Для последовательности cat, dog, cat начинаем с пустого словаря. Первое cat получает счётчик 1. Для dog создаётся отдельный ключ со значением 1. Второе cat находит прежнюю запись и увеличивает её до 2. Число ключей равно 2, а сумма счётчиков равна 3. Это два разных свойства, и оба полезны для проверки.

Если вместо увеличения всегда присваивать единицу, словарь превратится в подобие множества: информация о повторениях потеряется. Если считать отсутствие ключа ошибкой, придётся явно разделить первое и повторные вхождения либо использовать предусмотренное языком значение по умолчанию.
## Порядок и воспроизводимый вывод
Не полагайся на порядок словаря, если контракт выбранного языка или конкретного контейнера его не гарантирует. Даже если порядок вставки сохраняется, он не равен сортировке по имени или по частоте. Для отчёта сначала сформулируй порядок, затем явно отсортируй результат с правилом разрешения равных значений.

Усложнение: вывести три наиболее частых слова, а при одинаковой частоте упорядочить их по алфавиту. Отдельно обработай случай, когда различных слов меньше трёх. Для большого потока сравни полную сортировку всех ключей и поддержание небольшой структуры лучших кандидатов.

# iteration
## От последовательности к конвейеру преобразований
Обход описывает порядок получения элементов, фильтрация — условие их сохранения, преобразование — новый элемент для каждого подходящего исходного, свёртка — объединение результатов в одно значение. Эти этапы можно выразить циклом или библиотечными операциями, но смысл должен оставаться одинаковым.

Разделяй вычисление значения и побочный эффект. Получить квадраты чётных чисел — вычисление; напечатать каждый квадрат — действие с внешним потоком. Если смешать их без необходимости, повторное использование логики и тестирование усложнятся. Особенно важно понимать, выполняется ли конвейер немедленно или только во время последующего обхода.

Ленивое вычисление может экономить память и прекращать работу после первых результатов. Но оно также означает, что изменение исходной коллекции, ошибка или побочный эффект могут наблюдаться позже создания самого конвейера. Для повторного использования иногда нужна материализация результата; она должна быть осознанной, потому что создаёт дополнительные данные.
## Фильтрация, квадрат и сумма
Рассмотрим [1,2,3,4]. Фильтр чётности оставляет [2,4]. Преобразование в квадрат даёт [4,16]. Свёртка сложением с начальным значением 0 даёт 20. Если поменять порядок и сначала возвести числа в квадрат, проверка чётности здесь случайно сохранит ответ, но это не универсальное свойство преобразований.

Чтобы увидеть влияние порядка, возьми условие «число меньше 4». Фильтрация до возведения в квадрат оставит 1,2,3 и сумму 14. Фильтрация квадратов по тому же порогу оставит только 1. Одинаково выглядящее условие относится к разным стадиям данных.
## Проверка повторного обхода
Запусти один конвейер дважды и выясни, повторяются ли вычисления, допускается ли повторное использование и сохраняется ли результат. Итератор, поток и обычная коллекция имеют разные контракты. Проверь пустой вход: сумма обычно равна нулю, но поиск первого элемента может вернуть отсутствие или ошибку.

Усложнение: обработать файл чисел так, чтобы хранить только текущую строку и несколько счётчиков. Сравни память потокового решения и решения, которое сначала загружает весь файл в список. Не называй ленивым алгоритм, который внутри скрыто материализует все данные.

# records
## Модель данных объединяет связанные факты и правила
Запись о товаре может содержать id, название и остаток. Хранить эти сведения в трёх отдельных параллельных массивах опасно: удаление из одного массива без соответствующего изменения остальных разрушит связь. Запись позволяет обращаться к целому понятию, а коллекция записей — хранить набор таких объектов.

Наличие полей ещё не делает модель корректной. Нужно определить инварианты: id уникален и устойчив, название не пустое, остаток неотрицателен. Одни правила можно обеспечить конструктором или проверкой входа, другие требуют контроля операций изменения. Если любой код может произвольно менять все поля, формальное наличие типа почти не защищает данные.

Разделяй идентичность и совпадение содержимого. Два экземпляра с одинаковым названием не обязательно обозначают один товар. Напротив, одна запись после переименования может оставаться тем же товаром благодаря id. Это различие влияет на поиск, сравнение, обновление и сохранение.
## Разбор операции выдачи товара
Пусть в записи id = 17, название «Тетрадь», остаток 5. Запрос выдать 3 единицы допустим и приводит к остатку 2. Запрос выдать 7 должен завершиться отказом и оставить 5. Запрос выдать отрицательное количество нельзя использовать как скрытое пополнение: вход требуется проверить отдельно.

Контракт удобно выразить операцией изменения остатка, а не прямым присваиванием поля из любого участка программы. Тогда проверка количества, достаточности остатка и обновление выполняются в одном месте. В C это может быть функция над структурой; в объектном языке — метод или отдельный сервис с ясным интерфейсом.
## Независимость представлений
Формат хранения и интерфейс модели не обязаны совпадать. В файле может быть строковое имя поля, в программе — специализированный тип; при импорте нужны проверки. Индекс записи в текущем списке нельзя использовать как вечный id: после сортировки позиции меняются.

Усложнение: реализовать резервирование товара и отмену резерва. Определи разницу между физическим остатком и доступным количеством, а затем запиши инварианты модели. Тестируй не только каждую операцию, но и цепочки: резервирование, отмена, повторная отмена.

# errors
## Ошибка имеет причину, контекст и договорённый результат
Не все неудачи одинаковы. Некорректный пользовательский ввод можно попросить исправить; отсутствие файла может требовать выбора другого пути; нарушение внутреннего инварианта обычно указывает на дефект программы. Прежде чем выбирать исключение или код результата, определи, кто способен разумно обработать ситуацию.

Неуспешная операция не должна незаметно превращаться в корректное значение. Если чтение настроек завершилось ошибкой, возврат пустой структуры может создать впечатление, что пользователь ничего не сохранял. Иногда значение по умолчанию допустимо, но это должно быть явно записано в контракте и отличаться от потери данных.

Сохраняй первоначальную причину и добавляй полезный контекст на границах: какой путь открывали, какую операцию выполняли, какая строка данных оказалась неверной. При этом диагностика не должна раскрывать пароли, токены или лишние персональные сведения. Ловить все ошибки и печатать «что-то пошло не так» удобно только для сокрытия информации от самого разработчика.
## Разбор преобразования возраста
Ввод «двадцать» не проходит числовой разбор. Ввод 999 успешно преобразуется в целое, но нарушает предметный диапазон. Отсутствие строки является третьей ситуацией. Разделив их, можно получить понятные сообщения и проверить каждую ветвь отдельно.

Если возраст сначала записывается в общую модель, а затем проверяется, ошибка оставляет модель в неправильном состоянии. Надёжнее получить временное значение, проверить все условия и только после этого зафиксировать изменение. Такой подход пригодится и для чтения файла, и для обновления нескольких связанных полей.
## Восстановление не равно игнорированию
Повтор операции полезен для некоторых временных отказов, но не исправляет неверный формат. Бесконечный повтор только скрывает исходную причину. При повторе ограничивай число попыток и учитывай, могло ли предыдущее действие уже произойти: повторная запись платежа отличается от повторного чтения файла.

Усложнение: загрузить каталог из файла, не испортив текущую рабочую копию при ошибке в середине документа. Сначала разбери и проверь новый набор полностью, затем замени состояние. Добавь тест, где первые записи корректны, а последняя повреждена: частичное обновление недопустимо.

# files
## Файл — внешний ресурс с собственной жизнью
Путь обозначает место поиска, а не гарантирует существование или доступность объекта. Открытие, чтение, запись и закрытие могут завершаться ошибками. Проверка существования перед открытием не устраняет гонку: между двумя операциями внешний мир способен измениться. Надёжный код проверяет результат самой нужной операции.

У текстового файла есть кодировка, у строк — правила разделения, у формата — версия и структура. Выбор UTF-8 нужно явно закрепить там, где API это позволяет. Относительный путь отсчитывается от рабочего каталога процесса, а не автоматически от папки исходного файла. Поэтому программа может работать из IDE и не находить данные после запуска из другого места.

Ресурс нужно своевременно закрывать. В управляемом языке сборщик мусора не заменяет договорённое освобождение файлового дескриптора. Языки предлагают разные механизмы: проверяемый fclose, RAII, using, try-with-resources, with или defer. Важно понимать, в какой момент механизм срабатывает и как передаётся ошибка финальной записи.
## Надёжное сохранение небольшого документа
Простая запись поверх исходного файла опасна: при сбое останется частичный документ. Один из распространённых подходов — подготовить новый файл в том же каталоге, полностью записать его и лишь затем заменить старый. Совпадение файловой системы важно для свойств переименования. Требования к устойчивости при отключении питания дополнительно зависят от синхронизации файла, каталога и платформы.

Атомарная замена не является резервным копированием. Она защищает от некоторых частичных состояний, но не спасёт от логически неверной новой версии. Поэтому резервная копия и проверка восстановления — отдельные задачи.
## Контрольные эксперименты
Проверь отсутствующий файл, пустой файл, кириллицу, путь с пробелами и неправильный формат. Для записи проверь отказ доступа и повторный запуск программы после успешного сохранения. Сравни прочитанный смысл документа с исходной моделью, а не только факт существования файла.

Усложнение: обработать журнал больше доступной памяти. Читай его частями и сохраняй незавершённую строку между блоками. Разделение слова или UTF-8 последовательности границей буфера не должно приводить к потере данных; при выбранной ASCII-модели это ограничение следует прямо указать.

# json
## JSON описывает форму документа, но не все правила приложения
Парсер проверяет синтаксис: кавычки, скобки, разделители и допустимые виды значений. После этого приложение всё ещё должно проверить схему. Поле stock может существовать и иметь строковый тип вместо числа; числовое поле может быть отрицательным; идентификаторы могут повторяться. Валидный JSON не равен корректной модели.

Объект JSON связывает строковые имена со значениями, массив сохраняет последовательность. Отсутствующее поле и явный null могут иметь разный смысл. Не все типы языка напрямую представимы: даты, множества, двоичные данные и пользовательские объекты требуют выбранного соглашения. Большие целые могут терять точность в средах с ограниченным числовым представлением, поэтому долговременные идентификаторы нередко сохраняют строками.

Версия схемы нужна для управляемого изменения формата. Новая программа должна различать отсутствие версии, известную старую версию и неизвестную будущую. Нельзя угадывать миграцию только по тому, что документ «похож». Миграция преобразует смысл и затем проходит те же проверки, что и новый документ.
## Разбор импорта каталога
Документ содержит version = 1 и массив books. Для каждой записи сначала проверяем наличие id и title, затем их типы, потом непустое название и уникальность id. Только после проверки всего документа заменяем рабочий каталог. Если последняя запись некорректна, прежние данные должны сохраниться.

Проверка обратного преобразования тоже важна: модель сохраняется, затем загружается из другого экземпляра программы. Сравниваются записи, идентификаторы и значения, а не пробелы и порядок ключей в JSON. Красивое форматирование документа не должно влиять на его смысл.
## Совместимость и безопасные границы
Не выполняй импортированный текст как исходный код. Ограничивай допустимый размер и глубину вложенности по требованиям приложения. Не сериализуй все внутренние поля автоматически: временные кэши, секреты и детали реализации могут не относиться к пользовательскому экспорту.

Усложнение: добавить необязательную категорию книги во второй версии формата. Опиши миграцию старых записей, значение категории по умолчанию и поведение при будущей неизвестной версии. Сохрани старый тестовый документ, чтобы следующая переработка не разрушила совместимость незаметно.

# modules
## Граница модуля уменьшает объём необходимых знаний
Хорошее разделение не измеряется количеством файлов. Модуль должен объединять связанную ответственность и скрывать детали, которые не нужны вызывающему коду. Если для вызова операции хранения приходится знать устройство консольного меню, направление зависимостей выбрано неудачно.

Полезно отделять вычислительное ядро от внешних эффектов. Ядро проверяет модель и выполняет операции над данными. Адаптер хранения читает и пишет документ. Интерфейс получает команды и показывает результат. При таком разделении ядро можно тестировать без реального диска и использовать в нескольких интерфейсах.

Установка пакета, импорт и сборка — разные действия. Импорт не гарантирует, что внешняя библиотека уже доступна. Воспроизводимость зависит от версии среды, зависимостей, конфигурации и команд запуска. Во встроенном исполнителе DevCat доступны стандартные библиотеки и файлы проекта; дополнительные сетевые зависимости не устанавливаются автоматически.
## Разделение небольшой программы статистики
Сначала есть один файл: вводит числа, вычисляет среднее и печатает ответ. Выдели функцию вычисления, принимающую последовательность. Затем оставь ввод и форматирование в точке входа. Теперь один клиент может печатать число, другой сохранять отчёт, а тест вызывать вычисление напрямую.

Если функцию перенесли, но она продолжает обращаться к глобальной переменной из исходного файла, зависимость не исчезла. Сделай необходимые данные параметрами. При циклическом импорте спроси, не смешаны ли ответственности: общий контракт или модель часто должны находиться на более низком уровне.
## Проверка самостоятельности границ
Собери проект из чистого каталога, а не только после множества запусков в IDE. Удали неиспользуемый файл и проверь, не зависит ли результат от старого выходного артефакта. Переименуй модуль и выполни предусмотренные проверки импортов. В C/C++ отдельно различай объявление, определение и связывание единиц трансляции.

Усложнение: реализовать два хранилища одного каталога — в памяти и в файле. Вычислительная логика должна использовать согласованный интерфейс, а не проверять повсюду конкретный вид хранилища. Докажи это тестом, который запускается без файловой системы.

# testing
## Тест проверяет наблюдаемое обещание
Полезный тест начинается с причины: какой дефект он должен обнаружить. Далее задаются вход, ожидаемое поведение и проверка. Если ожидаемый результат вычислен тем же алгоритмом, что и тестируемая функция, общая ошибка способна пройти незамеченной. Для небольших примеров вычисляй ответ независимо вручную или простым эталонным способом.

Примеры, границы и свойства дополняют друг друга. Пример фиксирует конкретное поведение. Граничный случай проверяет переход между режимами. Свойство связывает несколько запусков: сортировка не меняет количество элементов, повторная нормализация не меняет результат, перевод между счетами сохраняет общую сумму. Ни один из видов не заменяет все остальные.

Тест должен быть воспроизводимым. Для случайных входов сохраняй seed и найденный минимальный контрпример. Часы, сеть и файловая система усложняют воспроизведение; их либо контролируют через зависимости, либо выделяют в отдельные интеграционные проверки. Модульные тесты вычислений не обязаны зависеть от наличия интернета.
## Набор для факториала и суммы
Факториал 0 равен 1, 1 равен 1, 5 равен 120. Первый случай проверяет нейтральное начальное значение, второй — минимальный непустой шаг, третий — несколько итераций. Дополнительно для допустимых n можно проверить связь factorial(n) = n × factorial(n−1), учитывая диапазон типа.

Для суммы 1…n свойство sum(n) − sum(n−1) = n обнаруживает многие нарушения границы цикла. Но если обе функции ошибочно добавляют постоянную одинаковую величину, разность её скроет. Поэтому нужны и прямые примеры, в частности sum(0) = 0. Свойства имеют свои ограничения и должны быть частью набора, а не универсальным доказательством.
## Проверка качества самих проверок
Намеренно внеси дефект: пропусти последний элемент, начни максимум с нуля или верни константу. Набор должен упасть с понятной причиной. Если не падает, добавь конкретный тест, обоснованный этим дефектом. Не улучшай отчёт количеством почти одинаковых примеров.

Усложнение: сравнить быстрый алгоритм поиска подмассива с медленным перебором на сотне небольших воспроизводимых входов. Медленный вариант здесь допустим как независимый оракул, потому что размеры специально ограничены. Сохрани обнаруженные расхождения как постоянные регрессионные случаи.

# debugging
## От симптома к проверяемой гипотезе
Сообщение об ошибке описывает наблюдение, но не всегда первопричину. Нарушенная структура данных может проявиться значительно позже ошибочной записи. Поэтому зафиксируй точный вход, ожидаемый результат, фактический вывод и условия запуска. Без воспроизводимого случая легко исправить соседний фрагмент и принять случайное изменение поведения за успех.

При ошибке компиляции начинай с первой содержательной диагностики. Одна пропущенная скобка способна породить десятки вторичных сообщений. При исключении или аварийном завершении изучи стек и значения на границах функций. При логической ошибке ищи первый момент, когда состояние перестало соответствовать инварианту.

Гипотеза должна предсказывать результат эксперимента. «Наверное, проблема в цикле» слишком расплывчато. «Верхняя граница исключает последний делитель, поэтому квадрат простого числа ошибочно считается простым» позволяет выбрать конкретный тест и ожидаемое поведение.
## Ошибка проверки простого числа
Числа 0 и 1 не являются простыми по определению: у простого натурального числа ровно два положительных делителя. После отдельной проверки n < 2 можно искать делитель от 2 до квадратного корня включительно. Для 49 нужно проверить 7. Условие d × d < n пропускает его, а d × d <= n включает.

Для большого ограниченного целого произведение d × d может переполниться раньше сравнения. При положительных d и n можно использовать d <= n div d. Исправление границы и исправление переполнения — разные изменения, и каждое требует своего обоснования.
## Уменьшение примера и регрессия
Если ошибка найдена в большой таблице, постепенно удаляй строки, сохраняя проявление. Минимальный пример делает причинную связь заметнее. Изменяй одну гипотезу за раз, фиксируй наблюдения и удаляй временный вывод из протокола автоматического ответа.

Усложнение: выбрать ошибочное решение из прошлой работы и оформить отчёт из четырёх частей: симптом, минимальный вход, причина, регрессионная проверка. Заверши не словами «теперь работает», а объяснением, почему исправление восстанавливает нарушенное свойство для всего допустимого класса входов.

# complexity
## Асимптотика объясняет рост, а измерение — конкретную реализацию
Сначала определяют размер входа и основную операцию. Для массива это часто число элементов n; для графа нужны как минимум число вершин V и число рёбер E; для текста может быть важно число байтов или символов. Без этого обозначение O(n) не имеет ясного смысла.

Асимптотическая верхняя оценка описывает порядок роста. Линейный обход выполняет работу, пропорциональную числу элементов; полный перебор пар даёт квадратичный рост; деление диапазона пополам приводит к логарифмическому числу шагов. Константы, кэш, распределение данных и устройство среды влияют на реальное время, поэтому асимптотика не заменяет измерений.

Сложность операции внутри цикла тоже входит в оценку. Один видимый цикл с поиском по списку на каждом шаге может оказаться квадратичным. Дополнительная память включает вспомогательные коллекции и стек рекурсии; входные данные обычно считают отдельно, если это явно оговорено.
## Сравнение поиска повторов
Попарная проверка массива рассматривает примерно n(n−1)/2 пар. Для n = 1000 это 499500 сравнений, для 2000 — 1999000: почти четырёхкратное увеличение. Решение с множеством делает один проход и обычно требует ожидаемого линейного времени, но использует дополнительную память и зависит от свойств хеширования.

Если необходимо вывести повторы в отсортированном порядке, понадобится учесть и сортировку результата. Если разрешено менять исходный массив, можно отсортировать весь вход и сравнивать соседей: O(n log n) времени, с дополнительными деталями памяти выбранной сортировки. Это пример нескольких разумных решений при разных требованиях.
## Как измерять без самообмана
Измеряй серию размеров и несколько повторов, отделяй подготовку данных и компиляцию от обработки. Для JIT-сред учитывай прогрев. Не делай вывод по одному маленькому примеру: накладные расходы способны полностью скрыть тенденцию. Сравнивай одинаковые условия и проверяй правильность результата после оптимизации.

Усложнение: реализовать три решения одной задачи — перебор, сортировку и хеширование. Опиши ограничения, при которых предпочёл бы каждое. Более сложная структура данных оправдана конкретным выигрышем или необходимой операцией, а не только модным названием.

# search
## Двоичный поиск является следствием инварианта
Линейный поиск последовательно проверяет элементы и работает без сортировки. Двоичный поиск использует упорядоченность или другой монотонный признак, чтобы на каждом шаге исключить часть кандидатов. Если такое свойство отсутствует, выбрасывание половины диапазона не имеет обоснования.

Для нижней границы удобно поддерживать полуоткрытый диапазон [left,right). Искомая позиция может оказаться и за последним элементом. При выборе середины сравниваем значение с целью: если оно меньше, исключаем середину вместе с левой частью; иначе сохраняем середину как возможный ответ и сдвигаем правую границу. Диапазон на каждом шаге должен строго уменьшаться.

Сортировка требует согласованного сравнения. Компаратор не должен случайно менять данные или нарушать транзитивность. Равенство по ключу не обязательно означает одинаковые объекты. Стабильная сортировка сохраняет относительный порядок равных ключей, но это свойство нужно проверять у выбранного алгоритма и API.
## Поиск первой позиции для повторяющегося значения
В массиве [1,3,3,7,9] нижняя граница 3 находится на позиции 1. Обычный поиск любого совпадения может вернуть позицию 2 и всё равно удовлетворить другому контракту. Поэтому до кода уточни, нужен ли любой элемент, первый, последний или место вставки.

Для цели 10 нижняя граница равна длине 5: это допустимый ответ о месте вставки, но не допустимый индекс чтения. Для пустого массива ответ 0. Для цели 0 ответ тоже 0. Дополнительная проверка найденного значения выполняется только после проверки, что позиция меньше длины.
## От поиска элемента к поиску ответа
Можно искать не только индекс. Если при вместимости C грузы помещаются в k контейнеров, то при большей вместимости это обычно тоже возможно. Получается монотонный предикат, по которому ищут минимальный подходящий ответ. Перед применением обязательно докажи эту монотонность и выбери границы с известным смыслом.

Усложнение: реализовать lower_bound без библиотечного поиска, затем найти количество вхождений как разность верхней и нижней границ. Проверь пустой вход, все одинаковые значения и цель за пределами массива. Сохрани инвариант в комментарии так, чтобы по нему можно было восстановить алгоритм.
