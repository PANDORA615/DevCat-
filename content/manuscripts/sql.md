# basics
## Таблица, строка и смысл SELECT
Реляционная таблица описывает один вид фактов. В customers одна строка представляет покупателя, в orders — отдельный заказ. Столбцы задают атрибуты, ключи помогают различать записи и выражать связи. Позиция на экране не является идентификатором: без ORDER BY результат не имеет обещанного порядка.

SELECT описывает требуемый результат, а не пошаговый цикл по физическим страницам. Сначала определи гранулярность: одна строка ответа — покупатель, заказ или итоговая группа? Затем выбери нужные столбцы и условия. SELECT * удобен при исследовании, но в стабильном интерфейсе явный список полей защищает от случайного изменения формы ответа при развитии схемы.

Проверь запрос на пустой таблице и таблице с несколькими одинаковыми именами. Одинаковое имя не превращает двух покупателей в одну сущность. Усложнение: описать контракт результата для списка покупателей так, чтобы другой человек мог написать независимую проверку.

# projection
## Выражение вычисляется для строки результата
Проекция выбирает поля и вычисляемые значения, не обязательно меняя число строк. Псевдоним даёт понятное имя столбцу ответа, но не переименовывает исходный столбец таблицы. Его доступность в других частях запроса зависит от контекста и диалекта, поэтому не полагайся на случайно допускаемое расширение.

Для вычисления скидки сначала уточни числовое представление и округление. В SQLite тип результата арифметики зависит от операндов; деление целых может не дать ожидаемую дробь. NULL участвует в вычислениях по отдельным правилам и часто переносит отсутствие в результат.

Сравни исходный amount, удвоенное amount и строковую подпись. Названия столбцов должны отражать единицы измерения. Проверь ноль, граничную сумму и отсутствующее значение в собственной базе. Усложнение: подготовить явный контракт столбцов для экспорта, который не зависит от порядка полей в схеме.

# filters
## Фильтр сохраняет только истинные условия
WHERE проверяет условие для исходных строк логического этапа запроса. В результат проходят строки с TRUE; FALSE и UNKNOWN не проходят. Это важно для NULL: условие amount > 50 не включает строку с неизвестной суммой, но не утверждает, что эта сумма обязательно меньше порога.

Для границы 50 различай > и >=. Строки с суммой 49, 50 и 51 образуют минимальный полезный набор проверки. Несколько строк с одной подходящей суммой не должны случайно схлопываться, если задача не требует DISTINCT.

Отдельно сформулируй, что фильтруется: каждый заказ или итоговая сумма покупателя. Второй вариант обычно требует агрегации и другого этапа условия. Проверка результата на демонстрационной таблице недостаточна, если в ней нет значений на границе и покупателя с несколькими заказами.

# logic
## Скобки выражают требуемую область условия
AND, OR и NOT соединяют предикаты; стандартный приоритет не заменяет явных скобок в бизнес-правиле. Условие A OR B AND C обычно группируется как A OR (B AND C). Если нужно (A OR B) AND C, результат на части строк будет другим.

В SQL логика трёхзначна. TRUE OR UNKNOWN даёт TRUE, FALSE AND UNKNOWN — FALSE, а отрицание UNKNOWN остаётся UNKNOWN. Поэтому законы привычного булева рассуждения нужно применять с учётом отсутствующих значений.

Составь таблицу строк, где каждый простой предикат бывает истинным, ложным и неизвестным. Включи случай, который проходит первую часть OR, но нарушает общее ограничение C. Именно он отличит два варианта скобок. Усложнение: переписать сложное отрицание через законы де Моргана и подтвердить равенство на данных с NULL.

# null
## Отсутствие значения нельзя сравнивать как обычное число
NULL обозначает отсутствие или неизвестность в выбранной модели. Сравнение через = NULL не является проверкой наличия: результат такого сравнения обычно UNKNOWN. Нужны IS NULL и IS NOT NULL. Пустая строка и ноль остаются обычными значениями и не должны автоматически заменять отсутствие.

COALESCE выбирает первое не-NULL значение. Это полезно для представления нулевого числа заказов или подписи отсутствующей категории, но замена может изменить смысл вычисления. Неизвестная цена и действительно нулевая цена различаются.

COUNT(*) считает строки, COUNT(column) — ненулевые значения столбца. После LEFT JOIN строка без совпадения всё ещё существует, поэтому подсчёт «заказов» через COUNT(*) даст лишнюю единицу. Используй идентификатор заказа и проверь покупателя без заказов отдельно.

# order
## Порядок должен быть полным для воспроизводимого ответа
ORDER BY задаёт сортировочные ключи по приоритету. При равенстве первого ключа применяется следующий. Если все указанные ключи равны, взаимный порядок таких строк может не быть определён. Для стабильной пагинации обычно добавляют уникальный id.

Сортировка по тексту зависит от правил сравнения и выбранной collation. Не считай, что порядок букв всегда совпадает с бытовым ожиданием для любого языка. NULL тоже имеет правила расположения, зависящие от диалекта и формы запроса.

Для списка заказов по убыванию суммы добавь id как второй ключ. Создай два равных заказа и проверь повторные запуски. Усложнение: объяснить различие сортировки результата и ORDER BY внутри окна: оконный порядок определяет расчёт, но не всегда внешний порядок выдачи строк.

# limit
## Страница результата требует устойчивого порядка
LIMIT ограничивает число возвращаемых строк. Без ORDER BY это не означает «первые по времени» или «самые важные»: такого смысла в запросе нет. OFFSET пропускает строки отсортированного результата и может становиться дорогим на больших смещениях.

Если между запросами данные меняются, страницы через OFFSET способны пропустить или повторить записи. Для некоторых интерфейсов подходит keyset-пагинация: следующая страница выбирается после последнего полного сортировочного ключа. Порог должен учитывать все части порядка, например amount и id.

Проверь пустую страницу, последнюю неполную страницу и несколько строк с равным основным ключом. Усложнение: написать условие следующей страницы для порядка amount DESC, id ASC и объяснить каждую часть сравнения. Случайное добавление только id меняет смысл при равных суммах.

# distinct
## Удаление повторов меняет смысл результата
DISTINCT применяется к выбранной комбинации столбцов. DISTINCT name может объединить разные записи людей с одинаковым именем. DISTINCT id, name сохраняет различия по id. Поэтому перед использованием определи, повторяется один факт из-за устройства запроса или существуют разные факты с одинаковыми видимыми значениями.

Дубликаты после JOIN часто указывают на отношение один-ко-многим. Механическое добавление DISTINCT способно скрыть проблему, но не исправить неверную сумму и не восстановить потерянный смысл строки.

Сравни число строк до и после добавления заказа существующему покупателю. Если запрос должен выдавать покупателей, наличие нескольких заказов может требовать EXISTS или предварительной агрегации. Усложнение: построить пример, где DISTINCT случайно удаляет законные разные записи, и выбрать ключ, сохраняющий их идентичность.

# range
## Границы и наборы значений требуют отдельной проверки
BETWEEN включает обе границы. Для диапазона от 20 до 50 подходят и 20, и 50. Для временных интервалов часто удобнее полуоткрытая форма: дата >= начало AND дата < конец. Она позволяет задавать соседние периоды без перекрытия, если тип и формат времени выбраны корректно.

IN проверяет принадлежность набору значений, но присутствие NULL в наборе влияет на UNKNOWN, особенно при отрицании NOT IN. Если нужно отсутствие связанной строки, часто яснее NOT EXISTS с явным условием связи.

Подготовь значения непосредственно за границами и на них. Для IN проверь повтор элемента списка и NULL. Усложнение: объяснить на конкретных строках, почему NOT IN с неизвестным значением может не вернуть ожидаемого покупателя.

# like
## Шаблон текста не равен обычному равенству
В LIKE знак процента обозначает последовательность символов, подчёркивание — один символ по правилам диалекта. Если пользователь ищет буквальный процент или подчёркивание, нужен согласованный механизм экранирования. Передача значения параметром защищает от инъекции, но не отменяет семантику шаблона.

Чувствительность к регистру и поведение Unicode зависят от СУБД, collation и конфигурации. Не делай вывод о кириллице только по опыту с ASCII. Начальный wildcard также может изменить возможность использования обычного индекса.

Проверь пустой текст, точное совпадение, имя с искомым фрагментом посередине и буквальный спецсимвол шаблона. Усложнение: отдельно реализовать точный поиск и поиск по шаблону, явно обозначив пользователю разницу.

# case
## CASE создаёт категории по последовательности условий
CASE выбирает результат первой подходящей ветви. Перекрывающиеся пороги требуют продуманного порядка. Если сначала проверить amount >= 20, более строгая последующая проверка >= 100 в той же цепочке не будет достигнута для больших сумм.

Результаты ветвей должны иметь согласованный смысл и подходящие типы. Пропущенный ELSE может дать NULL, если ни одно условие не выполнено. Условие с UNKNOWN не выбирает ветвь как истинную.

Для категорий small, medium и large сначала нарисуй непересекающиеся интервалы. Проверь каждую границу и значение с NULL. Усложнение: использовать CASE внутри условной агрегации и различить количество подходящих заказов, сумму подходящих сумм и число покупателей с хотя бы одним подходящим заказом.

# aggregate
## Агрегация изменяет гранулярность
SUM, COUNT, AVG, MIN и MAX объединяют строки в итог. Без GROUP BY результат обычно относится ко всему отфильтрованному набору. С GROUP BY получается отдельный итог для каждой группы. Важно понимать, какие исходные строки входят в вычисление и какие значения пропускаются из-за NULL.

Для пустого набора COUNT даёт ноль, тогда как SUM и AVG обычно дают NULL. COALESCE может представить сумму как ноль, если это соответствует бизнес-смыслу. Среднее средних без весов обычно не равно общему среднему: группы могут иметь разное число записей.

Проверь пустые данные, одну строку, несколько строк и NULL. Усложнение: объяснить, почему после соединения с позициями заказа общая сумма заказа может быть посчитана несколько раз, и как изменить гранулярность до итогового SUM.

# group
## Ключ группы определяет, какие факты объединяются
GROUP BY образует группы по выбранным значениям. Группировка только по имени объединит разных покупателей с одинаковым именем, если это имя не уникально. Устойчивый id выражает сущность точнее. Поля в результате должны быть связаны с ключом группы или определённым агрегатом по правилам корректного запроса.

SQLite допускает некоторые неагрегированные поля вне GROUP BY, но полученное значение может не иметь требуемого смысла. Не используй случайно разрешённый синтаксис как способ получить «первую строку» группы. Для такой задачи нужны явный порядок и подходящий оконный или связанный запрос.

Добавь двух покупателей с одинаковыми именами и разным числом заказов. Проверь, не слились ли их итоги. Усложнение: сначала агрегировать заказы по customer_id, затем присоединить имя из customers и объяснить, почему у результата одна строка на покупателя.

# having
## Фильтр строк и фильтр групп работают на разных этапах
WHERE определяет, какие исходные строки попадут в группы. HAVING отбирает уже полученные группы по их итогам. Для покупателей с общей суммой более 100 нужно сравнивать агрегат; фильтр отдельных заказов amount > 100 решает другую задачу.

Рассмотри покупателя с двумя заказами по 60. У него нет отдельного заказа дороже 100, но общая сумма 120. Этот пример отличает запросы, которые случайно совпали на демонстрационных данных с одним заказом на покупателя.

Если нужно учитывать только заказы выбранного периода и затем выбрать активных покупателей, ограничение периода относится к исходным строкам, а условие числа заказов — к группам. Усложнение: сравнить две бизнес-формулировки, «покупатели с дорогими заказами» и «покупатели с большой суммой», и привести данные, где результаты различаются.

# inner
## Соединение создаёт пары строк по условию
INNER JOIN возвращает совпадающие пары, а не «приклеивает столбец по позиции». Для связи orders.customer_id = customers.id каждый заказ сопоставляется с соответствующим покупателем. У покупателя с несколькими заказами будет несколько строк, что естественно для гранулярности заказа.

Неверное условие или его отсутствие может создать декартово произведение. Случайное равенство номеров строк не является связью. Ключи и ограничения схемы помогают выразить допустимость отношений, но смысл самого запроса всё равно нужно проверить.

Вручную выпиши пары ключей для двух заказов одного покупателя и одного другого. Убедись, что покупатель без заказов не появляется в INNER JOIN. Усложнение: добавить ещё одну связь один-ко-многим и предсказать увеличение числа строк до выполнения запроса.

# left
## Внешнее соединение сохраняет левую строку без совпадения
LEFT JOIN дополняет отсутствующую правую часть значениями NULL. Это позволяет сохранить покупателя без заказов. Но последующий WHERE по полю правой таблицы может удалить такую строку и тем самым изменить смысл внешнего соединения.

Если нужны все покупатели и только их заказы дороже 50, условие правого соответствия обычно относится к ON. Если нужны только покупатели, у которых есть такой заказ, это другая задача и другой контракт. Разница становится видимой только на покупателе без подходящих заказов.

Для подсчёта используй COUNT(order.id), а не COUNT(*), когда нужно число настоящих заказов. Проверь нулевой итог и влияние COALESCE на сумму. Усложнение: показать результат до и после переноса условия между ON и WHERE на одном небольшом наборе.

# multiplicity
## Размножение строк следует из мощности отношений
Когда одна запись соединяется с несколькими строками справа, её значения повторяются в нескольких парах. Если затем сложить повторённую общую сумму, получится завышенный итог. Это не ошибка SUM: сумма правильно обрабатывает неверно выбранный набор строк.

Перед каждым JOIN запиши, что означает одна строка слева, справа и после соединения. Для двух независимых отношений один-ко-многим число сочетаний может перемножиться. Решение часто состоит в предварительной агрегации каждого источника до нужного уровня или использовании EXISTS для проверки факта наличия.

Не исправляй денежный итог через SUM(DISTINCT amount): два законных заказа могут иметь одинаковые суммы. Такая операция удалит нужное различие. Усложнение: создать покупателя с двумя одинаковыми заказами и двумя контактами, получить четыре пары и обосновать правильный способ сохранить сумму двух заказов.

# subquery
## Подзапрос выражает отдельное вычисление с контрактом формы
Подзапрос может возвращать одно значение, набор строк или служить источником в FROM. Скалярный контекст требует подходящей мощности результата; поведение нескольких строк и ограничения различаются по СУБД. Коррелированный подзапрос использует значения внешней строки и должен читаться с этой зависимостью.

Раздели вычисление среднего заказа и отбор заказов выше среднего. Сначала самостоятельно проверь скалярный итог, затем используй его в условии. Для корреляции явно назови внешний ключ, чтобы одинаковые имена полей не скрыли ошибку связи.

Оптимизатор может преобразовать форму запроса, поэтому нельзя надёжно оценить производительность только по числу уровней скобок. Усложнение: записать один понятный контракт через подзапрос и через предварительно агрегированный источник, сравнить результаты и планы на одинаковых данных.

# exists
## EXISTS проверяет наличие хотя бы одной подходящей строки
Для отбора покупателей с заказами не обязательно возвращать каждую пару покупателя и заказа. EXISTS выражает факт наличия и сохраняет гранулярность внешней строки. Содержимое списка SELECT внутреннего запроса обычно не является результатом EXISTS; важно, существует ли строка по условию.

Корреляция должна связывать внутреннюю запись с текущим покупателем. Если забыть orders.customer_id = customers.id, наличие любого заказа сделает условие истинным для всех покупателей. Демонстрационный набор без покупателей без заказов способен скрыть такой дефект.

Проверь одного покупателя с несколькими заказами, другого без заказов и пустую таблицу orders. Усложнение: выбрать покупателей с заказом дороже индивидуального порога и объяснить, почему результат содержит каждого подходящего покупателя один раз без DISTINCT.

# anti
## Отсутствие связи требует проверки того же контракта
NOT EXISTS выбирает внешние строки, для которых не найдено ни одной подходящей внутренней. Это удобно для покупателей без заказов или без заказа нужного вида. Важно отрицать правильный предикат: «нет дорогих заказов» не означает «вообще нет заказов».

Альтернативой иногда является LEFT JOIN с проверкой NULL в гарантированно ненулевом ключе правой таблицы. Проверка произвольного nullable-столбца может ошибочно принять настоящее совпадение за отсутствие. NOT IN также требует внимания к NULL в наборе.

Добавь покупателя только с дешёвыми заказами и сравни две формулировки отсутствия. Затем добавь неизвестное значение в учебный пример с NOT IN и объясни результат через трёхзначную логику. Усложнение: найти покупателей, не имеющих ни одного заказа, нарушающего условие, и отдельно решить, должны ли подходить покупатели без заказов.

# cte
## Именованные этапы делают гранулярность видимой
WITH позволяет дать имена промежуточным отношениям. Это полезно для разбиения отчёта на этапы: подходящие заказы, итоги по покупателю, ранжирование, окончательный вывод. Для каждого этапа укажи ключ и смысл строки; тогда легче обнаружить ошибочное размножение данных.

CTE не обязано означать физически сохранённую временную таблицу. Возможность материализации и преобразования зависит от СУБД, версии и формы запроса. Улучшение читаемости само по себе не является доказательством ускорения.

Проверь каждый этап отдельно небольшим SELECT, прежде чем соединять весь запрос. Усложнение: переписать сложный вложенный запрос через два-три содержательно названных CTE и доказать, что наборы строк, обработка NULL и порядок окончательного результата сохранились.

# sets
## Операции над наборами имеют разные правила кратности
UNION объединяет с удалением повторов, UNION ALL сохраняет вхождения. INTERSECT и EXCEPT выражают пересечение и разность по правилам набора соответствующей СУБД. Столбцы ветвей должны согласоваться по числу и смыслу; одинаковая позиция не делает разные единицы измерения совместимыми.

Если соединить два журнала событий через UNION, одинаковые видимые строки могут схлопнуться, хотя обозначают разные события. Если объединяются перечни уникальных сущностей, удаление повторов может быть как раз нужным. Выбор следует из идентичности факта.

Подготовь одну строку, присутствующую в обеих ветвях, и сравни число результатов. Итоговый ORDER BY относится к общему результату, а не автоматически к отдельной ветви. Усложнение: выразить проверку равенства двух результатов через симметрическую разность, отдельно учитывая, важны ли повторения строк.

# window
## Окно вычисляет контекст и сохраняет исходные строки
Оконная функция добавляет расчёт к строкам, не схлопывая их как обычный GROUP BY. PARTITION BY делит данные на независимые группы расчёта, ORDER BY задаёт порядок внутри окна, а рамка определяет набор строк для некоторых оконных агрегатов.

Одна строка может одновременно содержать сумму отдельного заказа и общую сумму заказов покупателя. Последняя будет повторяться для каждого заказа и не должна бездумно складываться повторно. Оконный ORDER BY не гарантирует внешний порядок отображения.

Сравни три формы: общую агрегацию, группировку по покупателю и SUM OVER(PARTITION BY customer_id). Выпиши число строк каждого результата. Усложнение: добавить фильтрацию по вычисленному рангу на внешнем этапе, не смешивая её с фильтром исходных заказов.

# ranking
## Равные значения требуют выбранного правила ранга
ROW_NUMBER присваивает разные номера строкам. RANK оставляет одинаковый ранг для равных ключей и пропускает следующие номера, DENSE_RANK не оставляет таких разрывов. Эти функции отвечают на разные вопросы: «ровно три строки» и «все записи трёх лучших уровней» могут дать разное количество результатов.

Если нужен воспроизводимый ROW_NUMBER, оконный порядок должен различать строки, например суммой и уникальным id. Но добавление id в порядок RANK устранит равенство, которое, возможно, было существенной частью задачи. Детерминированность и бизнес-смысл ранга нужно согласовать.

Проверь суммы 100,100,80: ранги будут различаться по выбранному правилу. Усложнение: выбрать лучший заказ каждого покупателя с сохранением всех равных лучших или ровно одного — и объяснить различие двух запросов.

# running
## Накопительный итог зависит от рамки окна
Для последовательности заказов накопительная сумма на текущей строке включает выбранную часть предыдущих строк. ROWS задаёт рамку по строкам, RANGE учитывает значения сортировочного ключа и группы равных значений в соответствии с правилами СУБД. При повторяющихся ключах результаты могут отличаться.

Для обычного последовательного итога удобно явно указать ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW и воспроизводимый порядок. Для скользящего окна нужно решить, считаются ли последние три записи или события за последние три дня: это разные рамки и разные требования к временным данным.

На суммах 10,20,5 ожидается последовательность 10,30,35 в выбранном порядке. Добавь одинаковые ключи сортировки и сравни явную ROWS-рамку с вариантом по умолчанию. Усложнение: вычислить скользящее среднее и обосновать обработку неполной рамки в начале группы.

# lag
## Соседняя строка определяется порядком, а не физическим местом
LAG и LEAD получают значение из предыдущей или следующей строки выбранного окна. Без осмысленного ORDER BY слова «предыдущая покупка» не имеют нужной определённости. PARTITION BY отделяет независимые последовательности покупателей или других сущностей.

Первая строка не имеет предыдущей в пределах группы. Возвращаемое отсутствие или заданное значение по умолчанию должно сохранять смысл: подстановка нуля может означать фиктивное предыдущее событие. Разницу сумм и временной интервал нужно интерпретировать отдельно.

Проверь одного покупателя с тремя заказами и другого с одним. Значение не должно перескакивать между группами. Усложнение: найти резкое изменение показателя, исключив первую строку каждой группы и явно обработав предыдущий нулевой показатель при расчёте относительного изменения.

# recursive
## Рекурсия строит последовательность отношений
Рекурсивный CTE содержит начальную часть и шаг, который получает следующие строки из уже найденных. Необходимы правило расширения и обоснование остановки. Для дерева это может быть переход к детям; для последовательности — достижение предельного числа; для графа с циклами нужен дополнительный механизм ограничения посещений.

UNION ALL сохраняет повторения и может бесконечно производить один и тот же цикл. UNION устраняет дубликаты полных строк, но добавленная глубина делает строки различными и способна разрушить ожидаемое прекращение. Поэтому «поставить UNION» не является универсальной защитой любой рекурсии.

Проследи начальную строку, первое и второе расширение вручную. Затем добавь цикл или повторную связь и объясни, что ограничивает работу. Усложнение: хранить путь с проверкой посещённых вершин для небольшой иерархии, документируя ограничение размера и стоимость строкового представления.

# schema
## Схема выражает допустимые факты и связи
Перед CREATE TABLE опиши сущности, их идентичность и отношения. Первичный ключ отличает строки, внешний ключ выражает ссылку на другую сущность, ограничения задают допустимые значения. Индекс строки в выводе и название объекта обычно не подходят в качестве универсального устойчивого ключа.

У таблицы должна быть ясная гранулярность. Для библиотеки книга как произведение и отдельный физический экземпляр могут быть разными сущностями. Если их смешать, становится трудно выразить одновременную выдачу двух экземпляров и независимое состояние каждого.

Сначала нарисуй несколько реальных примеров данных, затем проверь, можно ли выразить нужные сценарии без противоречий. Усложнение: добавить историю выдач и объяснить, какие факты относятся к книге, экземпляру, читателю и событию выдачи.

# constraints
## Проверка в приложении не заменяет ограничение базы
Несколько клиентов могут одновременно записывать данные. Если уникальность проверяется только предварительным SELECT, между проверкой и INSERT другая операция может создать конфликт. UNIQUE и другие ограничения позволяют базе проверять правило в момент изменения в соответствии с её механизмами.

CHECK ограничивает значения строки, NOT NULL — допустимость отсутствия, внешний ключ — ссылочную связь. В SQLite проверку внешних ключей нужно включать по правилам соединения; наличие текста REFERENCES не следует автоматически считать достаточным без проверки конфигурации.

Подготовь допустимую запись и отдельные нарушения каждого ограничения. Проверь не только сообщение об ошибке, но и сохранность остальных данных. Усложнение: описать правило «одна активная выдача на экземпляр» и выбрать подходящую схему или индекс с условием там, где он поддерживается.

# normalization
## Избыточность создаёт аномалии, а не только лишние байты
Если имя покупателя хранится в каждой строке заказа, переименование требует согласованного изменения всех копий. Нового покупателя без заказов может оказаться негде сохранить, а удаление последнего заказа способно удалить единственное описание покупателя. Это аномалии обновления, вставки и удаления.

Нормализация опирается на зависимости атрибутов и ключи. Выделение customers и ссылка customer_id отделяет факт о покупателе от факта о заказе. Однако механическое разбиение всех полей по отдельным таблицам не является целью: нужно сохранить возможность без потерь восстановить нужные отношения.

Денормализация иногда используется осознанно для конкретных запросов, но требует правил согласования и измеримого основания. Усложнение: взять таблицу с заказом, покупателем и несколькими товарами, перечислить зависимости и построить схему, где сумма строки не размножается случайным JOIN.

# insert
## Значения передаются отдельно от синтаксиса
INSERT должен перечислять смысл записываемых полей. Явный список столбцов уменьшает зависимость от порядка схемы. Для пользовательских значений применяются параметры клиентского API; текстовое склеивание строки не становится безопасным из-за ручной замены одной кавычки.

Параметр обозначает значение, а не произвольное имя таблицы или часть оператора. Динамический выбор столбца требует контролируемого набора допустимых вариантов. При пакетной записи нужно выбрать транзакцию, поведение конфликта и способ получения созданных идентификаторов по правилам СУБД.

Проверь название с апострофом, кириллицей, пустое обязательное поле и нарушение уникальности. Не сообщай успех до фактической фиксации. Усложнение: импортировать набор записей так, чтобы ошибка одной строки приводила к заранее описанному полному откату или отдельному отчёту, а не случайному частичному состоянию.

# update
## Условие изменения определяет область риска
UPDATE и DELETE затрагивают все строки, удовлетворяющие условию; отсутствие WHERE не означает «текущую строку интерфейса». Перед изменением полезно проверить выборку тем же ключевым условием и оценить ожидаемое число строк. Но отдельный предварительный SELECT не заменяет транзакцию и контроль конкурентных изменений.

Для обновления одной сущности используй устойчивый ключ. Название может повторяться и изменяться. Выражение SET должно сохранять инварианты, а результат операции — проверяться по принятому контракту, включая отсутствие записи.

Проверь ноль подходящих строк, ровно одну и намеренно несколько. Усложнение: оптимистическое обновление с номером версии: изменить запись только при совпадении id и ожидаемой версии, затем отличить конфликт от успешного результата. Не превращай нулевое число изменений в безусловное сообщение «сохранено».

# transactions
## Фиксация объединяет согласованный набор изменений
BEGIN, COMMIT и ROLLBACK задают границу транзакции. Несколько шагов логической операции должны завершиться вместе либо оставить допустимое прежнее состояние. Атомарность не означает, что произвольные действия с внешними файлами или сетью автоматически входят в ту же транзакцию.

Рассмотри перевод: проверить допустимость суммы, списать с одного счёта, зачислить на другой, зафиксировать. Ошибка между шагами не должна уменьшить общую сумму. Проверка остатка и изменение должны быть согласованы с выбранной моделью конкуренции, иначе два клиента могут опираться на одно старое значение.

Держи транзакции настолько короткими, насколько позволяет контракт. Не ожидай пользовательского ввода внутри открытого изменения. Усложнение: смоделировать отказ второй записи и проверить полный откат, после которого новая обычная операция всё ещё успешно выполняется.

# isolation
## Конкурентные операции могут наблюдать разные состояния
Уровень изоляции и режим блокировок определяют, какие взаимодействия допустимы. Нельзя переносить поведение одной СУБД и режима в другую по одному названию транзакции. SQLite имеет конкретную модель чтения и записи, а режим WAL меняет некоторые свойства взаимодействия, не превращая её в произвольный многопишущий сервер.

Потерянное обновление возникает, когда два клиента читают одно значение и затем независимо записывают вычисленный результат, затирая работу друг друга. Увеличение через согласованное выражение, условие версии или подходящая блокировка решают разные варианты задачи.

Нарисуй расписание двух клиентов по шагам: чтение A, чтение B, запись A, запись B. Проверь итог и сравни с требуемым. Усложнение: описать политику повторов при конфликте и доказать, что повтор всей операции не дублирует уже совершённый внешний эффект.

# indexes
## Индекс ускоряет конкретный доступ ценой поддержки
Индекс хранит дополнительную структуру для поиска или порядка. Он не ускоряет любой запрос автоматически и требует места и работы при изменениях. Выбирать индекс нужно по частым условиям, связям и сортировкам, а не просто добавлять его на каждый столбец.

Порядок полей составного индекса имеет значение. Условия равенства по префиксу и диапазон по следующему полю часто дают иной доступ, чем ограничение только последнего поля. Выражения, преобразования и правила сравнения тоже могут повлиять на применимость.

Сравни запрос до и после индекса на одинаковых данных, проверь план и время. Для маленькой таблицы полный просмотр может быть разумным выбором оптимизатора. Усложнение: подобрать индекс для фильтра по customer_id и порядка по amount, затем оценить влияние на скорость массовой вставки.

# plan
## План показывает выбранный способ, а не полное доказательство скорости
EXPLAIN QUERY PLAN в SQLite помогает увидеть просмотр, поиск по индексу и некоторые промежуточные операции. Формат вывода может зависеть от версии; не строй пользовательский контракт на случайном точном тексте строки плана.

Исследуй запрос с реальными типами и распределением данных. Одинаковое число строк при разной избирательности может привести к разной стоимости. Наличие слова INDEX само по себе не означает победу: важны число обработанных записей, дополнительные обращения и сортировка.

Измеряй несколько повторов в одинаковых условиях, учитывай кэш и стоимость подготовки. После переписывания сравни смысл ответа, NULL, повторы и порядок. Усложнение: найти запрос, который пользуется индексом, но остаётся медленнее разумной альтернативы, и объяснить причину по модели доступа.

# security
## Безопасная граница отделяет данные от команды
SQL-инъекция возникает, когда пользовательский текст становится частью синтаксиса запроса. Параметры передают значения отдельным каналом. Проверка предметного формата полезна, но не заменяет параметризацию: допустимое название может законно содержать апостроф.

Права базы и доступ приложения должны соответствовать нужным операциям. Read-only режим учебного исполнителя DevCat ограничивает учебную базу; собственная SQLite-база IDE допускает отдельные DDL/DML команды. Это свойство приложения, а не запрет самого языка SQL.

Не записывай секреты и реальные личные данные в демонстрационные выгрузки. Проверяй экспорт по составу полей. Усложнение: выделить контролируемый набор сортировочных столбцов для динамического отчёта и показать, почему параметр значения не может подставить произвольный ORDER BY.

# migration
## Изменение схемы должно учитывать существующие данные
Миграция задаёт переход между версиями, а не только создание новой пустой базы. Перед добавлением ограничения проверь, удовлетворяют ли ему старые строки. Для нового обязательного поля нужно определить смысл значения у уже существующих записей.

Храни последовательность переходов и версию схемы. Резервная копия полезна только при проверяемом восстановлении; экспорт таблиц и согласованная копия работающей базы имеют разные свойства. Для SQLite способ копирования зависит от режима работы и открытых соединений, поэтому простое копирование одного файла не всегда означает согласованный снимок.

Проверь миграцию на старом тестовом документе, повреждённой копии и повторном запуске. Усложнение: добавить версию формата и новую связь, сохранив id, и описать поведение при неуспехе посередине изменения.

# project
## Аналитика магазина соединяет модель и проверяемый отчёт
Сначала перечисли вопросы: выручка по покупателю, число заказов, средний чек, доля в общей сумме и активность по периодам. Для каждого укажи гранулярность, денежные единицы, обработку нулевого результата и порядок. Одна красивая таблица без контракта не позволяет проверить правильность.

Раздели исходные факты, агрегаты и представление. Сохраняй индивидуальные заказы при необходимости деталей и отдельно вычисляй итоги. Проверяй, что сумма групп согласуется с общей суммой там, где группы действительно образуют разбиение.

Сделай маленький набор с повторяющимися именами, равными суммами и покупателем без заказов. Рассчитай результаты вручную и только потом запускай запросы. Усложнение: показать два отчёта с разными бизнес-формулировками и объяснить, почему совпадение чисел на одном наборе не делает формулировки эквивалентными.

# graduation
## Итоговая база библиотеки должна переживать последовательность действий
Раздели книги, экземпляры, читателей и выдачи. У каждой сущности нужен устойчивый ключ, у связей — определённые ограничения. Сформулируй правила активной выдачи, возврата и истории. Не удаляй исторический факт только ради того, чтобы интерфейс выглядел пустым.

Построй сценарии добавления книги, выдачи экземпляра, повторной недопустимой выдачи, возврата и поиска просрочки. Для каждого зафиксируй изменение состояния и сообщение при отказе. Затем добавь миграцию и резервную копию, которые проверяются на отдельных экземплярах базы.

Итоговый проект оценивай не количеством таблиц, а согласованностью модели, сохранностью данных и объяснимостью запросов. Усложнение: два одновременных клиента пытаются выдать один экземпляр; опиши, какое ограничение и транзакция сохранят правило и как проигравший клиент узнает об отказе.
